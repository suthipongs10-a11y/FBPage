## 2. ปัญหาที่ audit เจอ และแก้แล้ว

### 2.1 Race condition → โพสต์ซ้ำในเพจลูกค้า

โค้ดเดิมเช็คว่า `target.fbPostId` ว่างแล้วค่อยยิง แต่ระหว่าง "อ่าน" กับ "ยิง"
มีช่องว่าง ถ้าคิวส่งงานเดียวกันให้ worker สองตัว (retry ซ้อน, worker restart,
หรือ cron tick ซ้อนกัน) ทั้งคู่จะเห็นว่ายังไม่มี `fbPostId` แล้วยิงพร้อมกัน

**แก้:** เพิ่ม `claimTarget()` เป็น atomic claim ที่ repository ต้อง implement เป็น

```sql
UPDATE post_targets SET status='publishing'
WHERE post_id=? AND page_id=? AND status NOT IN ('published','publishing')
```

พร้อม `releaseTarget()` ที่ถูกเรียกทุกทางที่ไม่ได้โพสต์จริง
(ไม่งั้นงานจะค้างสถานะ `publishing` ตลอดกาลแล้ว retry จะจองไม่ได้)

มีเทสต์ยิงสองงานพร้อมกันจริงๆ แล้วยืนยันว่า POST ออกไปครั้งเดียว

### 2.2 Approval Queue ยังไม่มีเลย

สเปกสั่งว่า *"ลูกค้ากดอนุมัติผ่าน Client Portal **หรือผ่าน LINE** (ปุ่ม อนุมัติ/แก้ไข)"*
โค้ดเดิม worker เช็ค `approvalStatus` แล้วข้ามถ้ายังไม่อนุมัติ — แต่ไม่มีอะไร
สร้างหรือเปลี่ยนสถานะนั้นเลย ฟีเจอร์จึงยังใช้จริงไม่ได้

**แก้:** เพิ่ม `ApprovalService`
- token เซ็น HMAC ผูกกับโพสต์ใบเดียวและการตัดสินใจเดียว (อนุมัติ/ขอแก้ใช้คนละ token)
- ลูกค้ากดจาก LINE ได้เลยโดยไม่ต้อง login แต่ปลอม token ไม่ได้
- หมดอายุ 14 วัน
- state machine กันข้ามขั้น และกันเปลี่ยนผลหลังโพสต์ขึ้นเพจแล้ว
- กดปุ่มเดิมซ้ำจากแชทเก่าไม่ error ให้ลูกค้าตกใจ

### 2.3 อัลบั้มคนละชุดได้ hash เดียวกัน

`typecheck` จับได้ว่าโค้ดส่ง `MediaItem[]` (object) เข้า `contentHash()` ที่รับ `string[]`
ผลคือ `join("|")` ได้ `"[object Object]|[object Object]"` — อัลบั้มทุกชุดที่มีรูป
จำนวนเท่ากันจะถูกมองว่าเป็นเนื้อหาเดียวกัน แล้วโดน duplicate guard บล็อกผิดๆ

**แก้:** เพิ่ม `hashableFromPost()` ที่ดึงเฉพาะ `url` ออกมา

## 3. การตัดสินใจเชิงออกแบบที่ตั้งใจให้ "ปลอดภัยไว้ก่อน"

### 3.1 แยก "ไม่เจอ" ออกจาก "เช็คไม่ได้"

ก่อน retry ระบบจะเช็คว่ารอบก่อนโพสต์ขึ้นไปแล้วหรือยัง (เผื่อกรณียิงสำเร็จ
แต่เน็ตขาดตอนรับ response) เดิมโค้ดคืน `null` ทั้งกรณี "ไม่เจอ" และ "เช็คไม่ได้"
ซึ่งทำให้ตอนโควตาเต็มระบบจะเข้าใจว่ายังไม่ได้โพสต์แล้วยิงซ้ำ

ตอนนี้แยกเป็น 3 สถานะ: `found` / `not_found` / `unknown`
- `unknown` → เลื่อนไปรอบหน้า ไม่ยิง
- `unknown` จนหมดรอบ → แจ้งเตือนให้คนเปิดเพจเช็คเอง ไม่เดาแล้วยิง

เหตุผล: โพสต์ช้าไปครึ่งชั่วโมงแก้ได้ แต่โพสต์ซ้ำในเพจลูกค้าลบทีหลังก็สายไปแล้ว

### 3.2 `noRetry` ที่ระดับ HTTP สำหรับทุกการโพสต์

gateway retry อัตโนมัติเมื่อเจอ 5xx ซึ่งดีสำหรับการอ่าน แต่อันตรายกับการโพสต์
เพราะ 5xx อาจเกิดหลัง Meta รับโพสต์ไปแล้ว การตัดสินใจลองใหม่จึงยกไปอยู่ที่
`PublishWorker` ที่เช็คก่อนได้ว่าโพสต์ขึ้นไปหรือยัง

### 3.3 ตัดสินใจจาก `action` ไม่ใช่เลข error

`retry-policy.ts` ไม่รู้จักเลข error ของ Meta เลยสักตัว — ดูแค่ `action`
(`throttle`/`retry` = ลองใหม่ได้, `reconnect`/`permission`/`fix_request`/`deprecated` = เลิก)
ความรู้เรื่องเลข error อยู่ที่ `packages/meta` ที่เดียว

ผลที่ได้: token ตายแล้วระบบเลิกลองทันที ไม่เสียเวลารอครบ 36 นาทีเพื่อได้ผลเดิม

## 6. ยังเหลือของ M-B (ตั้งใจเลื่อน)

- **BullMQ adapter** — `PublishQueue` เป็น interface แล้ว ตัวจริงต้องต่อ Redis
  ตรรกะทั้งหมดที่ผิดแล้วเจ็บ (โพสต์ซ้ำ/ผิดเพจ/retry) เทสต์ครบแล้วโดยไม่ต้องมี Redis
- **Prisma repository** — `PostRepository` / `ApprovalRepository` พร้อมให้ implement
  ข้อควรระวัง: `claimTarget` **ต้อง** เป็น atomic UPDATE ไม่ใช่ SELECT แล้ว UPDATE
- **หน้าปฏิทิน** — รอ `apps/web`
- **Media pipeline** — ตอนนี้รับ URL สาธารณะ (R2) ตรงๆ ตามที่สเปกวางไว้

## 7. สิ่งที่ต้องระวังใน M ถัดไป

1. `claimTarget` เป็น atomic operation — ถ้า implement เป็น SELECT-then-UPDATE
   จะกลับไปมีบั๊กเดิมโดยที่เทสต์ยังผ่าน (เพราะ in-memory repo ไม่มี race)
   ควรมีเทสต์ระดับ integration กับ Postgres จริงตอนต่อ Prisma
2. Reels ใช้โฮสต์ `rupload.facebook.com` และ header `OAuth` ไม่ใช่ `Bearer`
   — ถ้าเพิ่มการอัปสื่อแบบอื่นต้องผ่าน `host: "upload"` ของ gateway เท่านั้น
3. `ApprovalService` ต้องการ secret แยกจาก app secret ได้ (ตอนนี้รับเข้ามาทาง constructor)
