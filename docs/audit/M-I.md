## 2. บั๊กที่ audit เจอ

### 2.1 ปัญหาที่แกว่งตรงเส้นแบ่ง ทำให้ยิงแจ้งเตือนทุกรอบ

ตัวยกระดับความรุนแรงเขียนไว้ว่า "ถ้าครั้งก่อนไม่ใช่ `critical` แต่ตอนนี้ใช่
ให้ส่งทันทีโดยไม่ต้องรอรอบเตือนซ้ำ" ซึ่งถูกในเจตนา — webhook เงียบ 30 นาที
กับเงียบ 5 ชั่วโมงคนละเรื่องกันจริง

แต่เกณฑ์ยกระดับของ webhook คือ "เงียบเกิน 4 ชั่วโมง" และเวลาที่เงียบ
**คำนวณใหม่ทุกรอบ** ปัญหาที่อยู่ตรงเส้นพอดี (เงียบ 3 ชม. 58 นาที) จะสลับ
warning ↔ critical ทุกครั้งที่ worker รัน แล้วทุกครั้งที่ข้ามขึ้นจะนับเป็น
"ยกระดับ" → ส่งทุก 5 นาที ซึ่งคือสิ่งที่โมดูลนี้มีไว้เพื่อป้องกันพอดี

**แก้:** เก็บ `peakSeverity` (แรงที่สุดที่เคยแจ้งไปแล้ว) แล้วเทียบกับค่านั้น
แทนที่จะเทียบกับครั้งก่อน — ยกระดับได้ครั้งเดียวต่ออายุของปัญหาหนึ่งเรื่อง
ถ้าหายแล้วกลับมาใหม่ สถานะถูกล้าง จึงยกระดับได้อีกตามสมควร

เทสต์ที่จับ: สลับ warning/critical 12 รอบติด ต้องได้ 2 ข้อความ ไม่ใช่ 7

### 2.2 ที่เก็บในหน่วยความจำมีพฤติกรรมต่างจากที่เก็บจริง

`InMemoryAlertStore.listOpen()` คืน reference ของ object ที่เก็บอยู่ พอโค้ด
เรียกใช้แก้ค่าใน object นั้นก่อนเรียก `put()` ค่าก็ติดไปเองแล้ว —
แต่ถ้าเปลี่ยนไปใช้ที่เก็บจริงที่อ่านมาจาก DB การแก้จะไม่ติดจนกว่าจะ `put()`

เทสต์ที่รันบนที่เก็บในหน่วยความจำจะผ่านทั้งสองแบบ แล้วบั๊กจะโผล่ตอน
ต่อฐานข้อมูลจริงเท่านั้น ซึ่งเป็นบั๊กประเภทที่หายากที่สุด

**แก้:** `listOpen()` คืนสำเนา ให้พฤติกรรมตรงกับที่เก็บจริง

### 2.3 ประวัติตัวอย่างมีเวลาเดียวกันหมด

หน้า Ops Center ใส่ประวัติตัวอย่างด้วย `AuditLog.record()` ซึ่งประทับเวลา
จากนาฬิกาเสมอ — ทุกรายการจึงขึ้นว่า "ไม่ถึงนาทีที่แล้ว" ประวัติที่ทุกอย่าง
เกิดในวินาทีเดียวกันไม่ใช่ประวัติ

น่าสนใจตรงที่นี่คือ **ผลข้างเคียงของการออกแบบที่ถูก**: `record()` ไม่เปิดให้
ผู้เรียกกำหนดเวลาเองโดยเจตนา เพราะถ้าเปิด log ก็ใช้เป็นหลักฐานไม่ได้อีก

**แก้:** ข้อมูลตัวอย่างเขียนผ่าน `store.append()` ตรงๆ พร้อมคอมเมนต์กำกับว่า
โค้ดจริงห้ามทำแบบนี้ — เก็บคุณสมบัติของ `record()` ไว้ครบ

### 2.4 กด bulk แล้วประวัติด้านล่างไม่ขึ้น

Server action บันทึก audit สำเร็จ แต่หน้าไม่ถูกสั่งให้โหลดใหม่ ประวัติด้านล่าง
จึงยังเป็นชุดเดิม — คนที่กดจะคิดว่า audit ไม่ได้บันทึก ทั้งที่บันทึกไปแล้ว
ซึ่งทำลายความเชื่อมั่นในระบบที่มีไว้เพื่อเป็นหลักฐานพอดี

**แก้:** เรียก `revalidatePath("/ops")` หลังทำสำเร็จ

## 3. การย้ายโค้ด: ทำไมตัวตรวจปัญหาต้องออกจาก `apps/web`

`collectProblems()` เคยอยู่ใน `apps/web/src/lib/today.ts` เพราะตอนนั้น
มีผู้ใช้รายเดียวคือหน้าจอ

พอมี Alert Center ผู้ใช้กลายเป็นสองราย: หน้าจอที่คนเปิดดู กับ worker
ที่ยิงเข้า LINE ตอนไม่มีใครเปิดจอ ถ้าปล่อยให้แต่ละทางคำนวณเอง
วันหนึ่งจะได้คำตอบไม่ตรงกัน แล้วคนจะเชื่อทางไหนไม่ถูก —
ซึ่งแย่กว่าไม่มีการแจ้งเตือนเลย เพราะคนเชื่อว่ามีระบบคอยดูให้อยู่

(เป็นความผิดพลาดแบบเดียวกับที่เจอใน M-H ข้อ 2.4 — ตัวตรวจสองตัวที่ตอบ
คำถามเดียวกันแต่คนละคำตอบ)

ตอนนี้ `packages/ops/problems.ts` เป็นเจ้าของตรรกะ ส่วนใน `apps/web`
เหลือแค่ตัวแปลงรูปข้อมูล เทสต์เดิมของหน้าเว็บ 29 ตัวยังผ่านหมดโดยไม่ต้องแก้
ซึ่งเป็นหลักฐานว่าการย้ายไม่เปลี่ยนพฤติกรรม

## 4. Alert Center — ออกแบบรอบ "ทำยังไงไม่ให้คนปิดเสียง"

ปัญหาที่แท้จริงของฟีเจอร์แจ้งเตือนไม่ใช่การส่งข้อความ แต่คือ**ส่งเมื่อไหร่**
ระบบแจ้งเตือนตายด้วยวิธีเดียวเสมอ: เตือนถี่ → คนปิดเสียง → ตอนมีเรื่องจริง
ไม่มีใครเห็น

| กลไก | ทำอะไร | ป้องกันอะไร |
|---|---|---|
| ถอยห่างขึ้นเรื่อยๆ | 0 → 15 นาที → 1 ชม. → 4 ชม. → 12 ชม. → วันละครั้ง | เงียบ 6 ชม. ไม่ได้ 72 ข้อความ |
| ตัวสุดท้ายวนซ้ำ | ปัญหาค้างสามวันยังเตือนวันละครั้ง | เงียบไปเลย = ลืม |
| รวมข้อความ | เกิน 3 เรื่องรวมเป็นก้อนเดียว | token 8 เพจหมดพร้อมกัน = 1 ข้อความ |
| เรื่องด่วนแยกเสมอ | ไม่เอา critical ไปรวมกับ warning | "มี 6 เรื่อง" ทำให้คนเลื่อนอ่านทีหลัง |
| บอกตอนหาย | ส่ง "✅ กลับมาปกติ" | ถ้าไม่บอก คนต้องเข้าไปเช็คเองอยู่ดี |
| ไม่บอกของที่ไม่เคยเตือน | เคยส่งจริงเท่านั้นถึงบอกว่าหาย | ไม่งั้นได้ข่าวดีของเรื่องที่ไม่เคยรู้ว่ามี |
| ช่วงเวลาเงียบ | warning รอเช้า, critical ปลุกได้ | token หมดตอนตีสอง = โพสต์เช้าไม่ขึ้น ต้องรู้ |
| รับภาพรวมทั้งหมด ไม่ใช่เหตุการณ์ | รันซ้ำด้วยข้อมูลเดิมไม่ส่งซ้ำ | worker ตายกลางทางแล้วรันใหม่ได้ |

## 5. Audit Log — ออกแบบรอบ "ใช้เป็นหลักฐานได้"

สเปกเขียนเหตุผลไว้ตรงๆ ว่า **"ป้องกันข้อพิพาทกับลูกค้า"** เคสจริงที่จะเกิดคือ
ลูกค้าโทรมาบอก "ทำไมโพสต์นี้ขึ้น ฉันไม่ได้อนุมัติ" ถ้าตอบไม่ได้ว่าใครกดเมื่อไหร่
เอเจนซี่เป็นฝ่ายผิดโดยปริยาย

- **ไม่มีเมธอดแก้ไขในหน้าที่ของที่เก็บ** — มีแค่ append, query, purge
  ถ้าวันหนึ่งมีคนอยากเพิ่ม `update()` นั่นคือสัญญาณว่ากำลังทำลายคุณค่าเดียวที่ log นี้มี
  (มีเทสต์ยืนยันว่าแก้ object ที่ส่งเข้าไปหรือที่ query ออกมา ไม่กระทบของที่เก็บไว้)
- **ค่าที่บันทึกผ่าน `redact()` เสมอ** (กฎข้อ 3) เพราะการตั้งค่าที่เปลี่ยน
  อาจมีฟิลด์ที่เป็นความลับปนมาโดยไม่ตั้งใจ
- **ตัวการล้างตามอายุบันทึกตัวเอง** — ไม่งั้นแยกไม่ออกระหว่าง "ไม่มีเหตุการณ์
  ในช่วงนั้น" กับ "มีคนลบทิ้ง" ซึ่งเป็นคำถามแรกตอนมีข้อพิพาท
- **`record()` เข้มงวด / `recordSafe()` กลืน error** — เส้นทางที่ผู้ใช้กำลังรออยู่
  ใช้ตัวหลัง (DB สะดุดไม่ควรทำให้การอนุมัติล้ม) แต่**นับจำนวนที่ล้มไว้**
  เพราะ audit ที่หายเงียบๆ คือ audit ที่พึ่งไม่ได้
- **เก็บเฉพาะฟิลด์ที่เปลี่ยนจริง** — log ที่บันทึกค่าทั้งชุดทุกครั้งทำให้ต้องนั่งเทียบเอง
  ว่าอะไรต่าง ซึ่งคือเหตุผลที่คนเลิกอ่าน log

## 6. Bulk Actions — ฟีเจอร์ที่ประหยัดเวลาที่สุดและพังหนักที่สุดพร้อมกัน

กดครั้งเดียวแก้ 20 เพจคือเหตุผลที่คนเดียวดูแล 20 เพจไหว
แต่กดผิดครั้งเดียวก็พัง 20 เพจของลูกค้า 6 รายพร้อมกัน

- **ต้องดูตัวอย่างก่อนเสมอ** — `planBulkChange()` ไม่แตะอะไรเลย
  และ `applyBulkChange()` รับ **แผน** ไม่ใช่รายการเพจดิบ เพื่อให้สิ่งที่ถูกเปลี่ยน
  เป็นสิ่งเดียวกับที่คนเห็นตอนกดยืนยัน
- **ข้ามเพจที่ค่าตรงอยู่แล้ว** — ไม่งั้น audit จะมี 20 บรรทัดที่กลบ 3 บรรทัดที่เปลี่ยนจริง
- **เกินเกณฑ์ต้องยืนยันซ้ำ** — เกิน 5 เพจ หรือข้ามลูกค้าเกิน 2 ราย
  (แก้ 3 เพจของลูกค้า 3 รายอันตรายกว่าแก้ 3 เพจของลูกค้าเดียว)
- **ส่งเฉพาะฟิลด์ที่เปลี่ยนจริงของเพจนั้น** ไม่ใช่ patch ทั้งก้อน —
  เพจที่ตรงอยู่แล้วบางฟิลด์ไม่ควรถูกเขียนทับให้เกิด event ซ้ำ
- **ล้มบางเพจไม่ล้มทั้งชุด และไม่ย้อนคืนของที่สำเร็จไปแล้ว** — การย้อนคืนบางส่วน
  ทำให้สถานะสุดท้ายเดายากกว่าเดิม บอกให้ชัดว่าเพจไหนไม่ผ่านแล้วให้กดซ้ำเฉพาะเพจนั้น

**ข้อจำกัดที่รู้ตัว:** ถ้าค่าของเพจเปลี่ยนระหว่าง "ดูตัวอย่าง" กับ "กดยืนยัน"
ระบบจะเขียนทับตามแผนเดิม ยอมรับข้อนี้เพราะทางเลือกอีกทาง (คำนวณใหม่ตอนกด)
ทำให้สิ่งที่เกิดขึ้นจริงไม่ตรงกับสิ่งที่คนเห็นตอนกด ซึ่งอันตรายกว่า —
ถ้าจะแก้ให้ครบต้องใส่ optimistic lock ซึ่งรอ Prisma repository ก่อน

## 7. สรุปงานเช้า — ตัวที่ทำให้เกณฑ์ "< 2 ชม./วัน" เป็นจริง

สิ่งที่กินเวลาจริงไม่ใช่การทำงาน แต่คือการเปิดจอไปไล่ดูว่ามีอะไรต้องทำบ้าง
`buildDigest()` จึงประกอบข้อความเดียวที่เรียงตามลำดับที่ควรลงมือ
(ของพัง → เลย SLA → รอตอบ → รออนุมัติ → ของที่จะเกิดเอง)
และ **ยุบส่วนเกินเป็น "และอีก N"** เพราะสรุปที่ต้องเลื่อนสามหน้าก็คือจออีกจอหนึ่ง

เรื่องระดับ "ควรดูเมื่อว่าง" ขึ้นเฉพาะตอนไม่มีเรื่องด่วน — มีเรื่องพังอยู่แล้ว
ยังบอกเรื่องรองคือทำให้ไขว้เขว
