# M-L — หน้าจอฝั่งปฏิบัติการอ่านข้อมูลจริง

`STATUS.md` เขียนไว้เองว่านี่คือ "⚠️ ตัวกั้นที่ใหญ่ที่สุดตอนนี้" — และมันจริง
โมดูลโดเมนเขียนครบหมดแล้ว ตัวดึงข้อมูลทำงานอยู่ แต่**หน้าจอที่คนเปิดดูทุกวัน
ยังโชว์ข้อมูลสมมติ**

อาการที่เจ้าของโปรเจ็คเจอจริงตอนติดตั้งเสร็จ: เปิดหน้าแรกแล้วเห็น
**"มี 3 เรื่องที่พังอยู่ตอนนี้"** พร้อมชื่อเพจที่ไม่มีอยู่จริง

## เรื่องที่ต้องตัดสินใจ แล้วตัดสินใจแบบไหน

### 1. `pageId` สองความหมาย — กับดักที่รอดสายตา typecheck

`packages/store/src/token-repository.ts` เตือนเรื่องนี้ไว้บนหัวไฟล์แล้ว
และรอบนี้เกือบพลาดซ้ำ:

| ตาราง | `page_id` คืออะไร |
|---|---|
| `post_targets` · `comments` · `conversations` | UUID ภายในของเรา (มี foreign key) |
| **`meta_call_logs`** | **รหัสเพจของ Facebook** (ไม่มี foreign key) |

`meta_call_logs` ไม่มี FK **โดยตั้งใจ** เพราะ gateway ต้องเขียน log ได้ตั้งแต่
ก่อนที่จะมีแถว `Page` (เช่นตอนดึงรายชื่อเพจครั้งแรก) ค่าที่เขียนลงไปจึงเป็น
`pageId` ตามความหมายของ**โดเมน** = รหัสเพจของ Facebook

ถ้า query ด้วย UUID: **ได้ผลลัพธ์ว่างโดยไม่มี error** แล้วหน้าจอจะบอกว่า
"ไม่เคยชนโควตา API เลย" ตลอดกาล ทั้งที่ชนอยู่ทุกวัน

จับได้เพราะเขียนเทสต์ integration ที่**จงใจใส่ค่าคนละแบบ**ลงสองตาราง
แล้วยืนยันว่าผลลัพธ์แปลงกลับมาเป็น UUID ให้ UI ใช้ได้

### 2. เพจที่ "ยังไม่ได้เชื่อม" ≠ เพจที่ "เชื่อมแล้วพัง"

ทั้งสองอย่างคือ "ไม่มี token ที่ใช้ได้" เหมือนกัน แต่คนละปุ่มที่ต้องกด:
อันแรกกด "เชื่อมเพจ" อันหลังต้องไปหาว่าทำไมมันหลุด

จึงแยกเป็น `no_token` ออกจาก `expired` / `revoked` ตั้งแต่ชั้นแปลงข้อมูล

### 3. เพจมี token หลายชนิด — โชว์ตัวไหน

เพจหนึ่งมีได้ทั้ง page token และ system user token ถ้าหยิบตัวแรกที่ Postgres
คืนมา สถานะที่โชว์จะเปลี่ยนไปมาโดยไม่มีเหตุผล

เลือก **"ตัวที่แย่ที่สุด"** เพราะหน้าจอตอบคำถามว่า "เพจนี้มีอะไรต้องแก้ไหม"
ไม่ใช่ "มี token ที่ดีอยู่ไหม" — การโชว์แต่ตัวที่เขียวคือการซ่อนปัญหาไว้
จนถึงวันที่มันพัง

### 4. ยังไม่ sync ผู้ติดตาม (`null`) ≠ ไม่มีคนตาม (`0`)

ชั้น query คืน `null` ตรงๆ ชั้นแปลงค่อยยุบเป็น `0` ตอนรวมยอด
ถ้ายุบตั้งแต่ชั้นล่าง คนที่แค่ยังไม่ได้ sync จะเห็น "0 ผู้ติดตามรวม"
ซึ่งดูเหมือนข้อมูลจริงที่แย่มาก

### 5. เสาคอนเทนต์ — เลือกบอกตรงๆ ว่าไม่รู้

`packages/studio` วางแผนคอนเทนต์เป็นเสา (ให้ความรู้ / ขาย / มีส่วนร่วม /
เบื้องหลัง) แต่ตาราง `posts` **ไม่มีคอลัมน์นั้น** ข้อมูลหายตอนบันทึก

ทางเลือกที่มี:

1. เติมคอลัมน์ → แต่ยังไม่มีใครเขียนค่าลงไป ได้คอลัมน์ว่างเปล่า
2. เดาจากชนิดโพสต์ (`photo` = ?) → ไม่ได้แปลว่าอะไรเลย
3. **บอกตรงๆ ว่า "ยังไม่ได้ระบุเสา"** ← เลือกอันนี้

เพราะสัดส่วนเสาคือตัวเลขที่คนเอาไป**ตัดสินใจว่าจะเขียนอะไรต่อ** —
เดาผิดแล้วเขาวางแผนผิดตาม บันทึกไว้ใน `STATUS.md` ว่าต้องเติมคอลัมน์
**พร้อมกับ**ให้ตัวสร้างคอนเทนต์เขียนค่าลงไป ไม่ใช่ทำอย่างใดอย่างหนึ่ง

### 6. `/ops` ต่อครึ่งเดียว โดยตั้งใจ

ตัวเลขเพจกับรายการปัญหาต่อของจริงแล้ว แต่**แผงคำสั่งหมู่**กับ
**ประวัติการดำเนินการ**ยังวิ่งบนที่เก็บข้อมูลในหน่วยความจำ

เพราะสองอันนั้นเป็น**เส้นทางเขียน**ที่ไปแก้การตั้งค่าเพจจริง ต้องต่อพร้อม
ด่านยืนยันตัวตน ไม่ใช่ต่อทิ้งไว้เฉยๆ ระหว่างนี้ติดป้าย `<PartialDemoNotice />`
บอกตรงๆ ว่า "กดได้ ผลจะหายเมื่อรีสตาร์ท และยังไม่ไปแก้การตั้งค่าเพจจริง"

## audit เจออะไร

### 🔴 ข้อ 1 — `pnpm test` ทิ้งเพจปลอมไว้ในฐานข้อมูล

เจอตอนเตรียม audit: ล้างฐานข้อมูลจนเกลี้ยง รัน `pnpm test` แล้วนับใหม่

```
{ workspaces: 2, pages: 3, conversations: 1, posts: 1, callLogs: 5 }
```

`publish.integration.test.ts` · `inbox.integration.test.ts` ·
`store.integration.test.ts` ล้างข้อมูลใน `beforeEach` แต่**ไม่ล้างใน `afterAll`**
ข้อมูลของเทสต์**ตัวสุดท้าย**จึงค้างอยู่ตลอดไป

ตอนหน้าจอยังอ่านข้อมูลตัวอย่าง เรื่องนี้ไม่มีใครเห็น แต่รอบนี้เปลี่ยนให้อ่าน
ของจริงแล้ว — **คนที่รัน `pnpm check` บนเครื่องตัวเองจะเห็น "เพจ ก" "ครัวคุณยาย"
โผล่บนหน้าแรกพร้อมรายการปัญหาปลอม** ซึ่งคืออาการเดิมเป๊ะที่ทำให้ต้องมีป้าย
"ข้อมูลตัวอย่าง" ตั้งแต่แรก — กลับมาทางประตูอื่น

**แก้:** เติมการล้างใน `afterAll` ทั้งสามไฟล์ พร้อมคอมเมนต์อธิบายว่าทำไม
ยืนยันแล้วว่ารัน `pnpm test` ซ้ำได้ฐานข้อมูลเหลือศูนย์ทุกตาราง

### 🔴 ข้อ 2 — import ที่ `tsc` และ vitest ผ่าน แต่หน้าเว็บ 500

เขียน `workspace-mapping.ts` แล้ว import ค่าจริงจากไฟล์ข้างเคียง:

```ts
import { CLIENT_COLOR_COUNT, type ClientPage } from "./workspace.js";
```

`pnpm typecheck` ผ่าน · `pnpm test` ผ่าน · เปิดหน้าเว็บได้ **500**:

```
Module not found: Can't resolve './workspace.js'
```

บนดิสก์ไฟล์ชื่อ `workspace.ts` — `tsc` กับ vitest แปลงนามสกุลให้ แต่ webpack
ของ Next ไม่แปลง

**แล้วทำไมไฟล์ข้างๆ เขียนแบบเดียวกันไม่พัง** — เพราะ `today.ts` กับ
`demo-workspace.ts` เป็น `import type` **ล้วน** ซึ่ง TypeScript ลบทิ้งทั้งบรรทัด
ตอน compile bundler ไม่เคยเห็น ต่างกับ import ที่ดึงค่าจริงตอนรัน

**แก้:** ใช้ alias `@/lib/workspace` (ไม่ใส่นามสกุล) + เพิ่ม alias `@/` ให้
`vitest.config.ts` ให้ตรงกับ `apps/web/tsconfig.json`

**และกันไม่ให้กลับมา:** `apps/web/src/import-style.test.ts` สแกนทุกไฟล์ที่
Next เอาไปมัด แล้วห้าม import ค่าจริงแบบ relative ที่ลงท้าย `.js`
(ยกเว้นไฟล์เทสต์ — webpack ไม่เคยเห็นมัน)

ตัวตรวจรุ่นแรกเขียน regex เป็น `[\s\S]*?` ซึ่งลากข้ามหลาย import รวดเดียว
แล้วรายงานผิดว่า `import type` ที่ปลอดภัยเป็นตัวมีปัญหา — เปลี่ยนเป็น `[^;]*?`
และเพิ่มเทสต์ที่ทดสอบ**ตัวตรวจเอง** ไม่งั้นวันหนึ่ง regex พังแล้วเทสต์ผ่านตลอด
โดยไม่ตรวจอะไรเลย

### 🟡 ข้อ 3 — แถบข้างยังเขียน "(ตัวอย่าง)" ค้างอยู่

เอา `<DemoBanner />` ออกครบทุกหน้าแล้ว แต่ `layout.tsx` มีคำว่า "(ตัวอย่าง)"
เขียนไว้ข้างจำนวนเพจในแถบข้าง ซึ่งตอนนี้กลายเป็นคำโกหกกลับด้าน — ข้อมูลจริง
แต่ป้ายบอกว่าปลอม

เจอเพราะ audit ดูข้อความบนหน้าจริง ไม่ได้ดูแค่ว่า component ถูกลบครบไหม

### 🟡 ข้อ 4 — เทสต์ integration ของรอบนี้เองก็พังรอบสอง

เทสต์ฟีดเหตุการณ์ผ่านรอบแรก แล้วพังรอบสอง (`expected 1 to be 5`) เพราะ
`meta_call_logs` ไม่มี FK ให้ cascade ตอนลบ workspace แถวจากรอบก่อนจึงค้าง

**แก้:** ใช้ prefix เฉพาะ (`vitest-ws-`) กับรหัสเพจที่ไฟล์นี้ใช้ แล้วล้างเอง
ทั้งใน `beforeEach` และ `afterAll` — ยืนยันด้วยการรันติดกันสองรอบ

## ตรวจของจริงผ่านเบราว์เซอร์ — สามสถานะที่คนใช้จริงจะเจอ

เปิดเซิร์ฟเวอร์จริงแล้วยิง HTTP ทุกหน้า

### 1. ยังไม่ได้เชื่อมเพจ (เพิ่งติดตั้งเสร็จ)

```
✓ /  /inbox  /calendar  /ops  /pages ตอบ 200 ทุกหน้า
✓ หน้าแรกบอกว่ายังไม่ได้เชื่อมเพจ + มีลิงก์ไปหน้าตั้งค่า
✓ ไม่มีป้าย 'ข้อมูลตัวอย่าง' เหลืออยู่แล้ว
✓ ไม่มีชื่อเพจสมมติหลงเหลือ
✓ ไม่โชว์ 'เรื่องพังอยู่ตอนนี้' ทั้งที่ยังไม่มีเพจ
```

### 2. มีเพจจริงพร้อมข้อมูล

```
✓ นับเพจถูก (ดูแล 2 เพจ)
✓ ผู้ติดตามมาจาก insights จริง (12,300)
✓ หน้าเพจโชว์สถานะ token ที่แย่ที่สุด
✓ เพจที่ไม่มี token แยกออกจากเพจที่ token พัง
✓ บทสนทนาที่บอทดูแลไม่มาแย่งคิวคน (คิวที่ต้องตอบ 1 จาก 2)
✓ ปฏิทินมีโพสต์จริง + บอกตรงๆ ว่ายังไม่ได้ระบุเสาคอนเทนต์
```

### 3. ต่อฐานข้อมูลไม่ได้ — สถานะที่อันตรายที่สุด

อันตรายเพราะถ้าพลาด หน้าจอจะโชว์ศูนย์ทุกช่องแล้วดูเหมือน
**"ทุกอย่างเรียบร้อยดี"** ทั้งที่จริงคืออ่านข้อมูลไม่ได้เลย

```
✓ ทุกหน้ายังตอบ 200 ไม่ขึ้นหน้า 500 ของ Next
✓ บอกว่าอ่านข้อมูลไม่ได้ + บอกวิธีแก้ (docker compose up -d)
✓ เตือนว่า "ศูนย์ทุกช่องไม่ได้แปลว่าไม่มีงานค้าง"
✓ ไม่บอกผิดว่า 'ยังไม่ได้เชื่อมเพจ'
```

ข้อสุดท้ายคือเหตุผลที่ `WorkspaceNotice` ตรวจ `errorTh` **ก่อน** `empty`
เสมอ — ตอนต่อ DB ไม่ได้ `empty` เป็น true ด้วย ถ้าเช็คสลับกันคนจะได้
คำแนะนำผิด ("ไปเชื่อมเพจ" ทั้งที่ปัญหาคือฐานข้อมูลไม่ขึ้น)
