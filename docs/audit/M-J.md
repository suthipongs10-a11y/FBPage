# Audit M-J — apps/webhook + apps/worker + packages/queue

ตรวจเทียบกับ `PAGE-OS-SPEC.md` ข้อ 5 (สถาปัตยกรรม), M4 (ตั้งเวลาโพสต์),
M8 (Alert Center) และกฎ 8 ข้อใน `CLAUDE.md`

**ผลรวม: ผ่าน** — 1,532 เทสต์ผ่านทั้งหมด (76 ไฟล์), typecheck สะอาด
เจอบั๊ก 6 จุด แก้แล้วทั้งหมด — สองจุดในนั้นเป็นชนิด "พังเงียบ ไม่มี error ที่ไหนเลย"
ซึ่งเป็นชนิดที่โปรเจ็คนี้กลัวที่สุด

รอบนี้ต่างจากรอบก่อนตรงที่ **ทดลองรันของจริง** ไม่ใช่แค่รันเทสต์ — ยก Postgres

## 1. สิ่งที่รอบนี้ทำให้เป็นจริง

ก่อนรอบนี้ โดเมนทั้งหมดเขียนครบแล้วแต่ไม่มีใครเรียก — โพสต์ที่ตั้งเวลาไว้
นอนอยู่ใน DB ตลอดไปโดยไม่มี error ที่ไหน และ event จาก Meta ไม่มีที่ให้เข้ามา

| ส่วน | หน้าที่ | สถานะ |
|---|---|---|
| `apps/webhook` | รับ event จาก Meta → ตรวจลายเซ็น → เข้าคิว | ✅ |
| `packages/queue` | ที่เดียวที่รู้จัก BullMQ | ✅ |
| `apps/worker` | รัน cron + ยิงโพสต์ + ตรวจปัญหา | ✅ (บางส่วน — ดูข้อ 4) |
| `packages/store` | ที่เก็บของงานโพสต์บน Prisma | ✅ |

**พิสูจน์ด้วยการรันจริง** (log จริงจากเครื่อง):

ฝั่งรับ webhook ทดลองด้วย HTTP จริง (ไม่ใช่ `app.inject()`):

## 2. บั๊กที่ audit เจอ

### 2.1 กฎ jobId ของ BullMQ ที่ผ่านโดยบังเอิญบางแบบ 🔴

BullMQ ห้าม custom jobId มี `:` **ยกเว้น**ตอนแยกแล้วได้ 3 ท่อนพอดี
(ข้อยกเว้นไว้รองรับของเก่า) แล้วคีย์กันซ้ำของเราเต็มไปด้วย `:`

| คีย์ | ท่อน | ผล |
|---|---|---|
| `msg:m_1` | 2 | ❌ โยน error |
| `comment:c_1:add` | 3 | ✅ ผ่าน (บังเอิญ) |
| `reaction:mid:sender:react` | 4 | ❌ โยน error |
| `publish:p1:page1` | 3 | ✅ ผ่าน (บังเอิญ) |
| `publish:p1:page1:retry:2` | 5 | ❌ โยน error |

ความบังเอิญที่บางแบบผ่านคือส่วนที่อันตรายที่สุด: เทสต์ที่ลองแค่คอมเมนต์กับ
โพสต์รอบแรกจะเขียวหมด แล้วไปพังตอนมีคนกดไลก์ หรือตอนโพสต์ต้อง retry —
คือตอนรับ webhook จริง ไม่ใช่ตอนเทสต์

**แก้:** `toJobId()` แปลง `:` เป็น `-` แล้ว **ต่อท้ายด้วยแฮชของคีย์เดิม**
ที่ต้องมีแฮชเพราะถ้าแทนที่เฉยๆ `a:b` กับ `a-b` จะกลายเป็น jobId เดียวกัน
แล้วงานคนละใบจะถูกมองว่าซ้ำแล้วหายไปหนึ่งใบเงียบๆ

**กันไม่ให้กลับมา:** เทสต์ไล่ event ทุกชนิดที่ระบบรู้จัก + คีย์งานโพสต์ทั้งสองแบบ
ผ่านกฎเดียวกับที่ BullMQ ใช้ และมีเทสต์ integration ที่ยืนยันว่า **กฎนี้มีอยู่จริง**
(ส่งคีย์ดิบเข้าไปแล้ว BullMQ ปฏิเสธจริง) ไม่ใช่เราระวังเกินเหตุ

### 2.2 โพสต์ประเภท "ลิงก์" ล้มเหลวทุกใบโดยแก้ไม่ได้ 🔴

`posts` ไม่มีคอลัมน์เก็บ URL เลย แต่ `PostPublisher` โยน error ทันทีถ้า
`content.link` ว่าง — โพสต์ประเภทลิงก์จึงล้มทุกใบด้วยข้อความ
`'โพสต์ประเภท "ลิงก์" ต้องระบุ URL'` โดยไม่มีทางแก้ให้สำเร็จได้
เพราะไม่มีที่ให้ใส่ URL ตั้งแต่แรก

เป็นบั๊กที่ซ่อนอยู่ได้นานเพราะเทสต์ของ `PostPublisher` ส่ง `content` เข้าไปตรงๆ
ไม่ได้ผ่านฐานข้อมูล ช่องว่างจึงอยู่ตรงรอยต่อพอดี

**แก้:** เพิ่มคอลัมน์ `link` + ส่งต่อใน `toContent()` + เทสต์ที่อ่านกลับผ่าน DB จริง

### 2.3 โพสต์ค้างเป็น "กำลังยิง" ตลอดกาลถ้าใส่คิว retry ไม่สำเร็จ 🔴

เส้นทางที่พัง:

1. `findDue` หยิบโพสต์ → `markQueued` → `posts.status = publishing`
2. ยิงไม่สำเร็จแบบที่ลองใหม่ได้ → `markTargetFailed(terminal: false)` →
   เป้าหมายกลับเป็น `scheduled` แล้ว `PublishWorker` คืน `{kind:"retry"}`
3. ตัวจัดการงานต้องใส่งานกลับเข้าคิวเอง — **ถ้าจังหวะนั้น Redis สะดุด**
   การใส่คิวพัง งานถูกนับเป็นล้มเหลว จบ
4. สิ่งที่เหลือ: เป้าหมาย = `scheduled`, โพสต์แม่ = `publishing`
   แต่ `findDue` มองหาแต่ `status = "scheduled"` → **ไม่มีใครหยิบอีกเลย**

ไม่มี error ที่ไหน ไม่มี alert ไม่มีใครรู้จนลูกค้าถามว่าทำไมไม่มีโพสต์

**แก้:** `findDue` หยิบโพสต์ที่ค้างเป็น `publishing` เกิน 60 นาทีกลับมาด้วย
(ยาวกว่าตารางเวลา retry ทั้งชุด 1+5+30 = 36 นาที พอสมควร เพื่อไม่ให้ไปหยิบ
โพสต์ที่กำลังรอ retry ตามปกติมายิงซ้อน) และ `markQueued` ต้องเขียนทับแม้สถานะ
เป็น `publishing` อยู่แล้ว เพื่อดัน `updatedAt` ไปข้างหน้า — ไม่งั้นโพสต์ที่
เพิ่งหยิบกลับมาจะเข้าเงื่อนไข "ค้าง" อีกในนาทีถัดไป แล้วโดนยัดคิวซ้ำทุกนาที
ไม่มีที่สิ้นสุด

### 2.4 logger กลืนคำธรรมดาไปกับ token 🟡

เจอตอนรันจริง: log ตอนปิดระบบขึ้นว่า `"signal": "[REDACTED]"`
กฎ redaction เทียบคำว่า `sig` แบบ substring แล้วไปโดน si-g ใน `signal`

ไล่ต่อแล้วเจออีกหลายคำที่โดนกลืนไปเงียบๆ มาตลอด:

| คีย์ | ที่ซ่อน | ผลเสีย |
|---|---|---|
| `insights` | in-**sig**-hts | ตัวเลขทั้งโดเมน analytics หายจาก log |
| `authorName` | **auth**-orName | ชื่อคนคอมเมนต์หาย ไล่เคสไม่ได้ |
| `designId`, `assignee` | de-**sig**-nId | — |

การ redact เกินไม่ได้ทำให้ระบบไม่ปลอดภัย แต่ทำให้ log ใช้สอบสวนไม่ได้
ซึ่งพอถึงเวลาจริงก็เท่ากับไม่มี log

**แก้:** คำสั้น (`sig`, `auth`) เปลี่ยนไปเทียบแบบ "เต็มท่อน" — ตัดชื่อคีย์ตาม
`-` `_` `.` และ camelCase แล้วเทียบทีละท่อน ส่วน `signature` / `authorization`
ยังเทียบ substring เหมือนเดิม จึงไม่ได้เปิดช่องให้ความลับหลุดเพิ่ม
มีเทสต์ทั้งสองด้าน: อะไรที่ต้องรอด และอะไรที่ยังต้องโดน redact เหมือนเดิม

### 2.5 เทสต์ล้มแบบสุ่มเพราะสองไฟล์ล้างฐานข้อมูลทับกัน 🟡

พอมีไฟล์เทสต์ที่ต่อ DB เป็นไฟล์ที่สอง ทั้งคู่ล้างตารางแบบเหมารวมใน `beforeEach`
และ vitest รันไฟล์พร้อมกัน → ไฟล์หนึ่งลบข้อมูลของอีกไฟล์กลางคัน

อาการหลอกมาก: รันทีละไฟล์ผ่านทุกครั้ง รันทั้งชุดล้มประมาณ 1 ใน 5 ครั้ง

**แก้:** แต่ละไฟล์ใช้ชื่อ workspace ของตัวเอง แล้วลบเฉพาะของตัวเอง
(ที่เหลือถูกลบต่อแบบ cascade) — ยังรันขนานได้เต็มที่
ยืนยันด้วยการรันทั้งชุด 8 รอบติดกัน ผ่านหมด 1,532/1,532 ทุกรอบ

### 2.6 สีประจำเพจสลับกันทุกครั้งที่เพิ่ม/ลบเพจ 🟢

`colorIndex` คำนวณจากลำดับในผลลัพธ์ของ query ซึ่งเปลี่ยนทุกครั้งที่จำนวนเพจเปลี่ยน
คนที่จำสีไว้จะอ่านผิด

**แก้:** คำนวณจากรหัสเพจแทน — เพจเดิมได้สีเดิมเสมอ

### 2.7 `upsert` ของ Prisma ไม่ atomic 🔴

`markSeen()` เขียนด้วย `prisma.webhookSeen.upsert()` ซึ่ง**ดูเหมือน**ตรงความหมาย
ที่สุด แต่มันแปลเป็น "อ่านก่อนแล้วค่อยเขียน" ที่มีช่องตรงกลาง

เทสต์ที่จดคีย์เดียวกันพร้อมกัน 8 ครั้งจับได้: **6 ใน 8 ล้ม** ด้วย unique violation
เพราะทุกตัวอ่านแล้วเห็นว่า "ยังไม่มี" พร้อมกันแล้วต่างคน INSERT

เรื่องนี้สำคัญเพราะ worker หลายตัวหยิบ event เดิมพร้อมกันได้จริง
(BullMQ กู้งานที่ค้างคืนมาให้ตัวอื่นทำ) ถ้าปล่อยไว้ งานจะล้มทั้งใบเพราะ
"จดซ้ำ" ทั้งที่ประมวลผลสำเร็จไปแล้ว แล้ว BullMQ จะเอามาทำใหม่วนไป

**แก้:** `createMany` + `skipDuplicates` ซึ่งแปลเป็น
`INSERT ... ON CONFLICT DO NOTHING` — Postgres รับประกันให้ในคำสั่งเดียว

### 2.8 เทสต์ call log ที่ล้มแบบสุ่ม (บั๊กของเทสต์เอง) 🟡

เทสต์ `flush` นับ `metaCallLog.count()` ทั้งตาราง แต่เทสต์ก่อนหน้าใน
ไฟล์เดียวกัน **จงใจ** เรียก `record()` แล้วไม่ `flush()` เพื่อพิสูจน์ว่ามันไม่บล็อก

แถวจากเทสต์นั้นจึงลงมาถึงหลัง `beforeEach` ล้างตารางไปแล้วได้ ทำให้เทสต์ถัดไป
นับได้ 6 แทนที่จะเป็น 5 — ซ่อนอยู่ได้จนกระทั่งมีไฟล์เทสต์ที่ต่อ DB เป็นไฟล์ที่สาม
แล้วจังหวะเปลี่ยนพอที่จะโผล่

**แก้:** นับเฉพาะแถวของเทสต์ตัวเอง (แยกด้วย `path`) ไม่ใช่ทั้งตาราง

## 4. สิ่งที่ยังไม่ได้ต่อ และรู้ตัวว่ายังไม่ได้ต่อ

รอบนี้ตั้งใจไม่ซ่อนของที่ยังไม่เสร็จ — รอบ cron ที่ยังไม่มีของจริงถูก
**ลงทะเบียนไว้แล้วโยน `NotWiredError`** พร้อมข้อความว่าขาดอะไร งานจะไปกอง
ในรายการที่ล้มเหลวให้เห็นจากหน้าคิว ไม่ใช่กองอยู่ในคิวแบบที่ดูไม่ออกว่าต่างจาก
"ยังไม่ถึงคิว"

> รอบเสริมหลังตรวจงาน: `InboxStore` บน Prisma + ตัวหยิบคิว `webhook-events`
> เขียนเสร็จแล้วในคอมมิตถัดมา ทดลองรันครบวงจากคำสั่ง `curl` จริง →
> Redis → worker → Postgres และส่งซ้ำแล้วยังได้แถวเดียวทุกตาราง
> ระหว่างทางเจอบั๊กเพิ่มอีกสองจุด (ดูข้อ 2.7 กับ 2.8)

| รอบ | ยังขาด |
|---|---|
| `token-health` | ตัวไล่เช็ค token ทุกเพจที่เขียนผลกลับลง DB |
| `analytics-sync` | `InsightsRepository` บน Prisma |
| `morning-digest` | ปลายทางส่งข้อความ (LINE) ที่ต่อของจริง |
| `monthly-report` | ตัวสร้าง PDF + ปลายทางส่งลูกค้า |
| `purge-expired` | เรียก `purgeExpired()` ในรอบนี้ |

และคิวที่ยังไม่มีตัวทำงาน — `webhook-events`, `moderation`, `analytics`,
`token-health` — worker พ่น warning บอกไว้ตอนสตาร์ท

> ⚠️ ข้อควรระวัง: ตอนนี้ `apps/webhook` ยัด event เข้าคิว `webhook-events`
> ได้แล้ว แต่ยังไม่มีใครหยิบไปทำ ถ้าเปิดรับ webhook จริงตอนนี้ งานจะกองใน Redis

## 5. ข้อสังเกตที่ยังไม่ได้แก้ (ตั้งใจ)

### 5.1 call log ไม่มีแถวเมื่อ "ไม่มี token"

`meta_call_logs` มีไว้ตอบคำถาม "ทำไมโพสต์ไม่ขึ้น" แต่ `resolveToken()` โยน
error ตั้งแต่ก่อนยิง HTTP จึงไม่มีแถวถูกเขียน — และ "token หมดอายุ" คือ
สาเหตุที่พบบ่อยที่สุด

ไม่แก้ในรอบนี้เพราะเป็นดีไซน์ของ `packages/meta` (log ของ **HTTP call**
ไม่ใช่ log ของ "ความพยายามจะเรียก") และความล้มเหลวนี้ถูกบันทึกครบใน
`post_targets.error` + log ของ worker อยู่แล้ว ถ้าจะแก้ควรแก้เป็น
"log ทุกความพยายาม" ทั้งชุด ไม่ใช่ปะเฉพาะจุดนี้

### 5.2 `apps/webhook` ไม่มีตัวจำกัดอัตรา

endpoint เปิดสู่อินเทอร์เน็ตและคำนวณ HMAC ของ body ได้ถึง 5 MB
คนที่ยิงมั่วรัวๆ ทำให้เปลือง CPU ได้ ปกติกันที่ load balancer ซึ่งเป็นที่ที่
ควรกันอยู่แล้ว (และเป็นที่เดียวกับที่ต้องตั้ง mTLS ของ Meta)

### 5.3 `PrismaCallLog` เก็บงานที่ค้างไว้ไม่จำกัด

ถ้า DB ช้ากว่าอัตราการยิง call ชุดที่ค้างจะโตเรื่อยๆ ในหน่วยความจำ
ยังไม่เป็นปัญหาที่ 20–30 เพจ แต่ควรมีเพดานก่อนขยาย

### 5.4 `GracefulShutdown` ใช้เวลาจริง ไม่ใช่ Clock ที่ฉีดเข้ามา

ตั้งใจ — สิ่งที่วัดคือ "ผ่านไปกี่วินาทีจริง" ก่อนโดน SIGKILL
ถ้าใช้ `FakeClock` ค่าที่ได้จะไม่มีความหมาย
