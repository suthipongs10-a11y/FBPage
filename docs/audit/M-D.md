## 2. ปัญหาที่ audit เจอ

### 2.1 ผมใช้เมตริกที่ปลดระวางเองโดยไม่รู้ตัว (แก้แล้ว)

ผมตั้ง `page_consumptions_by_consumption_type` เป็นแหล่งของ "คลิกลิงก์"
ซึ่งอยู่ในตระกูล `page_consumptions` ที่ปลดระวางพร้อม reach/impressions มิ.ย. 2026

ตัวเช็คที่ผมเขียนไว้เองก็จับไม่ได้ เพราะเทียบชื่อแบบ **ตรงตัว** ส่วนชื่อจริง
มี suffix `_by_consumption_type` ต่อท้าย

**ทำไมเรื่องนี้แย่กว่าพัง:** Meta ไม่ตอบ error สำหรับเมตริกที่ปลดระวาง
มันแค่ไม่คืนข้อมูล → รายงานลูกค้าจะขึ้น "คลิกลิงก์: 0" ทุกเดือน
เราส่งรายงานผิดให้ลูกค้าไปเรื่อยๆ โดยไม่มีอะไรเตือน

**แก้:**
- เพิ่มการเช็คแบบ **ตระกูล** (`DEPRECATED_PREFIXES`) ไม่ใช่แค่ชื่อตรงตัว
- ถอด metaName นั้นออก และคำนวณ link clicks จากข้อมูลระดับโพสต์ที่เราเก็บเองแทน
- เพิ่มกฎในเทสต์สถาปัตยกรรม: ห้ามมีสตริงชื่อเมตริกที่ปลดระวางในโค้ดทั้งโปรเจ็ค
  ยกเว้นใน `metrics.ts` ที่เก็บไว้เพื่อปฏิเสธ

### 2.2 เรื่องที่ต้องยืนยันกับเอกสาร Meta ก่อนขึ้นจริง

ตอนนี้ `link_clicks` ไม่ได้ดึงจาก Meta แล้ว ผมเลือกให้คำนวณจากข้อมูลโพสต์ของเราเอง
**ยังไม่ได้ยืนยันว่าชื่อเมตริกใหม่ของ Meta สำหรับ page-level link clicks คืออะไร**

ผมเลือกทำแบบนี้แทนการเดาชื่อเมตริกใส่ไป เพราะถ้าเดาผิด ระบบจะเงียบและส่งเลข 0
ให้ลูกค้าโดยไม่มีใครรู้ ส่วนวิธีนี้อย่างน้อยตัวเลขที่ออกมาเป็นของจริงจากโพสต์เรา

**ต้องทำก่อนขึ้น production:** เปิดเอกสาร Graph API v25.0 ตรวจว่ามีเมตริกใหม่
สำหรับ link clicks ระดับเพจไหม ถ้ามีให้ใส่กลับเข้า `METRICS`

## 3. การตัดสินใจเชิงออกแบบ

### 3.1 ไม่ดึงข้อมูลของ "วันนี้"

sync ดึงถึงเมื่อวานเท่านั้น เพราะตัวเลขของวันที่ยังไม่จบจะเปลี่ยนอีก
ถ้าเก็บไว้แล้วไม่อัปเดต รายงานจะผิด — และถ้าอัปเดตทุกชั่วโมงก็เปลืองโควตาเปล่า

### 3.2 `end_time` ต้องถอยกลับหนึ่งวัน

Meta คืน `end_time` เป็น "ปลายช่วง" คือเที่ยงคืนของ**วันถัดไป**
ถ้าเอามาใช้ตรงๆ ข้อมูลทุกวันจะเลื่อนไปหนึ่งวัน — ผิดทั้งเดือนโดยดูเผินๆ ไม่ออก
มีเทสต์คุมไว้แล้ว

### 3.3 เมตริกที่เป็นอัตราส่วนต้องเฉลี่ย ไม่ใช่รวม

`bot_containment_rate` 0.6 ทุกวันเป็นเวลา 31 วัน ถ้าเอามารวมจะได้ 18.6
แล้วรายงานจะขึ้น "1860%" มีรายการ `AVERAGED` แยกไว้ พร้อมเทสต์

### 3.4 บอกตรงๆ เมื่อข้อมูลไม่ครบ

ถ้ามีข้อมูลไม่ถึง 80% ของเดือน รายงานจะขึ้นคำเตือนให้ลูกค้าเห็น
ไม่ใช่แสดงตัวเลขที่ต่ำกว่าความจริงเฉยๆ แล้วให้ลูกค้าเข้าใจผิดว่าเดือนนี้แย่ลง

### 3.5 รายงาน HTML แทน PDF library

ฟอนต์ไทยใน PDF library ส่วนใหญ่จัดการยาก สระลอยเพี้ยน วรรณยุกต์ซ้อนผิดที่
เบราว์เซอร์เรนเดอร์ไทยถูกต้องอยู่แล้ว จึงทำ HTML แล้วให้ headless Chromium แปลง

### 3.6 escape ทุกค่าที่มาจากข้อมูล

ชื่อเพจและข้อความโพสต์มาจากผู้ใช้ ถ้าไม่ escape จะกลายเป็นช่องโหว่ในไฟล์
ที่เราส่งให้ลูกค้าเอง มีเทสต์ยิง `<script>` เข้าไปทุกช่องทาง (ชื่อเพจ, เนื้อโพสต์,
ชื่อเอเจนซี่, สีแบรนด์)

## 4. เรื่องโควตา

งาน sync ใช้ `priority: "low"` ทุก call — ต้องไม่ไปเบียดงานตอบ inbox
หรือโพสต์ตามเวลาที่ลูกค้ารออยู่ (ระบบ priority ที่ทำไว้ตั้งแต่ M-A)

backfill จำกัดที่ 90 วันต่อรอบ กันกรณีเพจที่ไม่ได้ sync มานาน
ดึงย้อนหลังทีเดียวจนโควตาหมดแล้วงานอื่นทั้งวันพัง

## 5. ยังเหลือของ M-D

- **Competitor Watch** (ติดตามเพจคู่แข่ง 3 เพจ) — ยังไม่ได้ทำ
  ต้องใช้ Page Public Content Access ซึ่งต้องผ่าน App Review แยกอีกตัว
  จึงเหมาะจะทำหลังรีวิวผ่านแล้ว ไม่ใช่ตอนนี้
- **แปลง HTML → PDF จริง** — ใช้ headless Chromium ตอนมี `apps/worker`
- **ส่งอีเมล/LINE ทุกวันที่ 1** — ตัวสร้างรายงานพร้อมแล้ว รอ scheduler ของ worker
- **Prisma repository** — `InsightsRepository` เป็น interface
  schema มี `insights_daily` PK `(page_id, date, metric_key)` รองรับ upsert แล้ว

## 6. สิ่งที่ต้องระวังต่อไป

1. **เพิ่มเมตริกใหม่ต้องเช็คก่อนว่าอยู่ในตระกูลที่ปลดระวางไหม** — `isDeprecatedMetric()`
   เช็คให้แล้ว และเทสต์สถาปัตยกรรมสแกนทั้งโปรเจ็คอีกชั้น
2. **`AVERAGED` คือจุดที่พลาดแล้วรายงานผิดแบบเงียบๆ** — เพิ่มเมตริกที่เป็น
   อัตราส่วนหรือค่าสะสมต้องใส่ในรายการนี้ด้วย
3. **Competitor Watch ต้องรอ App Review** — อย่าใส่ไว้ในแผนที่สัญญากับลูกค้า
   จนกว่าจะรู้ผลรีวิว
