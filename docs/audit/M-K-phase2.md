## เรื่องที่ต้องตัดสินใจ แล้วตัดสินใจแบบไหน

### 1. ทำไมคัดลอกข้อมูลมาเก็บเอง แทนที่จะถาม Meta ตอนเปิดหน้าจอ

- Meta คิด rate limit **ต่อแอป** ถ้าเปิดแดชบอร์ดทีละ 40 call เปิดสิบครั้งก็ตัน
  แล้ว**งานที่ลูกค้ารออยู่จริง** (ตอบแชท, ยิงโพสต์ตามเวลา) จะโดนบล็อกไปด้วย
  เพราะใช้โควตาก้อนเดียวกัน
- เทียบย้อนหลังไม่ได้ถ้าไม่จด — Meta ให้ยอด ณ ปัจจุบันอย่างเดียว
- ค้นคอมเมนต์ด้วยคำ ทำบน Postgres ของเราได้ แต่ทำผ่าน Graph API ไม่ได้

### 2. ทุก call ใช้ `priority: "low"`

งานฟังเสียงไม่มีใครนั่งรอ — มีเทสต์ล็อกไว้ว่าทุก call ที่ออกจากโมดูลนี้ต้องเป็น
`low` ถ้าเผลอเปลี่ยนเป็น `normal` วันหนึ่งมันจะไปแย่งคิวของงานที่มีคนรอ

### 3. โพสต์ใช้ `upsert` แต่คอมเมนต์ใช้ `createMany` + `skipDuplicates`

ตั้งใจให้ต่างกัน:

- **โพสต์** ยอด engagement เปลี่ยนทุกชั่วโมง ถ้า `skipDuplicates` ยอดจะค้างที่
  ค่าตอนดึงครั้งแรกตลอดกาล แล้วแดชบอร์ดจะนิ่งสนิท**โดยไม่มี error ให้เห็นเลย**
- **คอมเมนต์** เขียนครั้งเดียวจบ และมีโอกาสเขียนชนกัน จึงต้องใช้
  `INSERT ... ON CONFLICT DO NOTHING` ที่ Postgres รับประกันในคำสั่งเดียว
  (`upsert` ของ Prisma เป็นอ่านแล้วค่อยเขียน — บทเรียนจาก `inbox-repository.ts`)

### 4. `ORDER BY last_fetched_at ASC NULLS FIRST`

Postgres เรียง `NULL` ไว้**ท้ายสุด**ตอน `ASC` เป็นค่าเริ่มต้น ถ้าไม่สั่ง
`nulls: "first"` เพจที่เพิ่งเพิ่มเข้ามาจะไม่ถูกดึงเลยจนกว่าเพจอื่นจะเก่าครบทุกตัว
— มีเทสต์กับฐานข้อมูลจริงล็อกไว้ เพราะเทสต์ในหน่วยความจำจับเรื่องนี้ไม่ได้

### 5. เพจที่ `source !== "META_API"` ข้ามไปเฉยๆ

ดึงเพจที่เราไม่ได้เป็นแอดมินต้องมีสิทธิ์ **Page Public Content Access**
ซึ่งต้องผ่าน App Review + Business Verification — ยิงไปก่อนก็โดนปฏิเสธเปล่าๆ
และเปลือง quota ตัวนี้จึงข้ามพร้อมบอกเหตุผลเป็นภาษาไทยกลับมา

## ที่ตรวจเจอตอน audit

### ✅ เดินเส้นทางจริงทั้งเส้น (ListeningSync → Prisma → Postgres)

จำลอง Graph API ที่มีโพสต์ 250 ใบ คอมเมนต์ 900 อัน พร้อม paging จริง:

| ตรวจอะไร | ผล |
|---|---|
| เพดานโพสต์ 100 ใบ บังคับจริง (API มี 250) | ✓ 100 |
| เพดานคอมเมนต์ 500 อัน บังคับจริง (API มี 900) | ✓ 500 |
| snapshot ผู้ติดตาม + อัปเดตค่าบนตัวเพจ | ✓ |
| จด `lastFetchedAt` จาก Clock ที่ฉีดเข้ามา | ✓ |
| **รันซ้ำแล้วข้อมูลไม่บาน** (100/500 เท่าเดิม) | ✓ |
| เพจแหล่งภายนอก — ไม่ยิงไป Meta เลย | ✓ 0 call |

**จำนวน call ต่อเพจ: 7** (1 ข้อมูลเพจ + 1 โพสต์ + 5 คอมเมนต์) สำหรับเพจที่มี
100 โพสต์และ 500 คอมเมนต์ — รอบละ 10 เพจจึงกินราว 70 call ต่อชั่วโมง

### ⚠️ เทสต์เดิมจับบั๊กได้ 2 จุด (แก้แล้ว)

**1. `apps/worker/src/handlers/cron.test.ts` — ตารางงานที่ไม่มีคนรับ**

เพิ่ม `listening-sync` เข้า `CRON_JOBS` แล้ว เทสต์เดิมฟ้องทันทีว่าไม่มีตัวจัดการ
ในชุดที่มันประกอบขึ้นมา ถ้าไม่มีเทสต์นี้ งานจะยิงทุกชั่วโมงแล้วล้มทุกชั่วโมง
โดยเห็นแค่ใน log ของโปรดักชัน

**2. `packages/meta/src/architecture.test.ts` — ใช้ `new Date()` ในโค้ดจริง**

เขียน `const now = new Date()` ใน `listening-repository.ts` เพื่อเก็บ `fetchedAt`
ซึ่งละเมิดกฎ "เวลาต้องมาจาก `Clock` ที่ฉีดเข้ามา" — ทำให้ `FakeClock` ไร้ความหมาย
และเทสต์ล็อกเวลาไม่ได้

**แก้:** ย้ายไปให้ `savePosts()` รับ `fetchedAtMs` จากตัวเรียก ที่เก็บข้อมูลไม่คิดเวลาเอง
เป็นการออกแบบที่ถูกกว่าเดิมด้วย — repository ไม่ควรมีความเห็นเรื่องเวลา
