## 2. บั๊กร้ายแรงที่ audit เจอ

### echo ใช้ `senderId` ทั้งที่ตอน echo ผู้ส่งคือ "เพจ" ไม่ใช่ลูกค้า

Meta ส่ง echo ของข้อความที่เพจส่งออกไป โดย **สลับฝั่ง**:
`sender` = เพจ, `recipient` = ลูกค้า

โค้ดเดิมใช้ `ev.senderId` หาบทสนทนาทุกกรณี ผลคือเมื่อเจ้าของเพจพิมพ์ตอบ
ในแอป Facebook ระบบจะไปสร้าง/พักบอทในบทสนทนาปลอม `p1:p1`
(เพจคุยกับตัวเอง) ส่วนบทสนทนาจริงกับลูกค้า **ไม่ถูกพัก**

ผลที่ตามมาคือ **บอทเด้งเข้าไปตอบซ้อนกลางบทสนทนาที่คนกำลังคุยอยู่**
ซึ่งคือบั๊กที่สเปกข้อ 6.3 และ 6.7 เตือนไว้ตรงๆ และเป็นเหตุผลที่ฟีเจอร์นี้มีอยู่แต่แรก

**แก้:** parse `recipient` เพิ่ม แล้วคำนวณ `contactId` ที่ parser
(`isEcho ? recipientId : senderId`) ให้ที่เดียวจบ ไม่ต้องให้ทุกจุดที่ใช้จำเอง

**ที่น่าสังเกต:** เทสต์เดิม 3 ตัวผ่านทั้งที่โค้ดผิด เพราะผมเขียน payload ทดสอบ
โดยให้ echo มี `sender` เป็นลูกค้า — ซึ่งไม่ตรงกับของจริง พอแก้บั๊กแล้วเทสต์พัง
จึงต้องเขียน helper `echo()` แยกที่บังคับให้ payload สมจริง

บทเรียน: เทสต์ที่สร้าง payload เองต้องสะท้อนรูปแบบจริงของ Meta
ไม่ใช่รูปแบบที่ทำให้โค้ดเราผ่าน

## 3. ฟีเจอร์ที่สเปกสั่งแต่ยังไม่ได้ทำ (เพิ่มแล้ว)

### 3.1 ตัวกรอง inbox (`filters.ts`)

สเปกระบุ 4 ตัวกรองไว้ชัดเจน ทำครบแล้วพร้อมนับจำนวนต่อตัวกรอง

จุดที่คิดเพิ่มจากสเปก: **เรียงตามความเร่งด่วน ไม่ใช่เวลาล่าสุด**
แอปแชททั่วไปเรียงตามข้อความล่าสุด แต่เป้าหมายของเราคือ "ตอบให้ทัน"
บทสนทนาที่เลย SLA ต้องขึ้นก่อนเสมอ แม้ข้อความจะเก่ากว่า

### 3.2 Escalation พร้อม deep link (`canned.ts`)

สเปก: "ส่ง LINE Notify หาคุณพร้อมลิงก์ deep link เข้า thread"

เพิ่มการจัดระดับความรุนแรง: ใกล้หมดหน้าต่าง 24 ชม. (< 2 ชม.) หรือเรื่องอ่อนไหว
→ `critical` เพราะพลาดแล้วตอบฟรีไม่ได้อีก

### 3.3 Canned replies (`canned.ts`)

แยกตามเพจ + ตัวแปร `{ชื่อลูกค้า}` `{ชื่อร้าน}` ตามสเปก

รายละเอียดที่ใส่ใจ: ตัวแปรที่ไม่มีค่าถูกตัดพร้อมช่องว่างที่ติดมา
ไม่ทิ้ง `{ชื่อลูกค้า}` หรือช่องว่างซ้อนไว้ให้ลูกค้าเห็น

## 4. กฎข้อ 7 และ 8 — บังคับจริง ไม่ใช่แค่เขียนไว้

`messaging-policy.ts` **โยน error** (ไม่ใช่คืน `allowed: false`) เมื่อ:
- บอทพยายามใช้ `HUMAN_AGENT`
- ใช้ legacy tag ที่ปลดระวาง 27 เม.ย. 2026

เหตุผลที่เลือก throw: สองกรณีนี้คือ **บั๊กของโค้ดเรา** ไม่ใช่สถานการณ์ปกติ
ที่ต้องรับมือ ถ้าคืนค่าเงียบๆ จะมีคนเผลอ `if (!allowed) return` แล้วปัญหาหายไป
โดยไม่มีใครรู้ว่ามีโค้ดที่ผิดกฎอยู่

เทสต์สถาปัตยกรรมจับได้ตอนไฟล์นี้เอ่ยชื่อ `HUMAN_AGENT` จึงปรับกฎให้เจาะจงขึ้น:
อนุญาตเฉพาะไฟล์ที่บังคับกฎ **และเพิ่มเทสต์พิสูจน์ว่าไฟล์นั้นตรวจผู้ส่งจริง**
ไม่ใช่แค่ได้สิทธิ์เอ่ยชื่อแท็ก

## 5. สเปกข้อ 6 — ปัญหาที่ต้องแก้ตั้งแต่ต้น

| ข้อ | สถานะ |

| 6.2 Echo loop | ✅ echo ของเราเองถูกข้าม |

เพราะ webhook ที่ตอบ error ซ้ำๆ จะถูก Meta ปิด subscription

## 6. การตัดสินใจเชิงออกแบบ

### SLA ไม่ถูกรีเซ็ตเมื่อลูกค้าพิมพ์รัว

`awaitingSinceMs` ยึดข้อความ **แรกสุด** ที่ยังไม่ได้ตอบ
ถ้ารีเซ็ตทุกครั้งที่ลูกค้าพิมพ์ต่อ ลูกค้าที่พิมพ์ถี่จะไม่มีวันเกิน SLA
ทั้งที่รอมาเป็นชั่วโมง — แต่หน้าต่าง 24 ชม. ยังขยับตามข้อความล่าสุด (คนละเรื่องกัน)

### ตรวจลายเซ็นจาก raw body เท่านั้น

มีเทสต์ยืนยันว่า body ที่เรียงคีย์ต่างกันแต่ข้อมูลเหมือนกัน **ต้องไม่ผ่าน**
พิสูจน์ว่าไม่ได้เผลอ parse แล้ว stringify ใหม่ (ซึ่งจะทำให้ลายเซ็นไม่มีความหมาย)

### คิวเรียงตาม "เหลือเวลาน้อยสุด" ข้ามเพจ

ลูกค้าแพ็กเกจ FULL (SLA 30 นาที) ที่ทักทีหลัง ได้ตอบก่อน STARTER (4 ชม.)
ที่ทักมาก่อน — นี่คือกลไกที่ทำให้ "คนเดียวดูแล 20 เพจ" เป็นไปได้จริง

## 7. ยังเหลือของ M-E

- **`apps/webhook`** (Fastify) — ตรรกะพร้อมทั้งหมด รอชั้น HTTP
  ข้อควรระวังตอนต่อ: ต้องเก็บ raw body ไว้ก่อน parse ไม่งั้นตรวจลายเซ็นไม่ได้
- **`unread` ใช้ read-modify-write** — ควรเป็น `UPDATE ... SET unread = unread + 1`
  ตอนต่อ Prisma ไม่งั้นข้อความที่มาพร้อมกันจะนับตกหล่น
- **Prisma repository** — `InboxStore` เป็น interface, schema รองรับครบแล้ว
  (`messages.mid` unique, `conversations.bot_paused_until`, `window_expires_at`)
- **Note ภายใน / PWA** — งาน UI

## 8. สิ่งที่ต้องระวังต่อไป

1. **`contactId` คือฟิลด์ที่ต้องใช้หาบทสนทนาเสมอ** ไม่ใช่ `senderId`
   — เพิ่ม event ชนิดใหม่ที่มีทิศทางสลับได้ ต้องคำนวณ `contactId` ที่ parser
2. **webhook ต้องตอบ 200 เสมอ** แม้ประมวลผลไม่สำเร็จ
   ตอบ error ซ้ำๆ = Meta ปิด subscription แล้วข้อความลูกค้าหายเงียบ
3. **`ACTION_RANK` ของ M-C และ `STATE_RANK` ของที่นี่** เป็นจุดตัดสินลำดับ
   เพิ่มสถานะใหม่ต้องกำหนดอันดับให้ถูก
