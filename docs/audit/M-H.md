## 2. บั๊กที่ audit เจอ

### 2.1 การตรวจคอนทราสต์สีที่ทำงานไม่ได้เลย

เขียนไว้ตอนแรกว่า "ถ้าตัวหนังสือบนปุ่มคอนทราสต์ต่ำกว่า 4.5 ให้เตือน"
โดยวัดสีแบรนด์เทียบกับสีตัวอักษรที่ `readableTextOn()` เลือกให้

**การตรวจนี้ยิงไม่ออกเลยแม้แต่ครั้งเดียว** เพราะทางคณิตศาสตร์:
- ตัวอักษรดำตกเกณฑ์เมื่อความสว่างของพื้น < 0.175
- ตัวอักษรขาวตกเกณฑ์เมื่อความสว่างของพื้น > 0.183

สองเงื่อนไขเป็นจริงพร้อมกันไม่ได้ ปุ่มจึงอ่านออกเสมอไม่ว่าลูกค้าเลือกสีอะไร
เป็นโค้ดที่ดูเหมือนป้องกันอะไรอยู่ แต่ไม่ได้ป้องกันอะไรเลย

**เรื่องที่พังจริง**คือตอนเอาสีแบรนด์ไปใช้เป็น *ตัวหนังสือหรือลิงก์บนพื้นขาว*
ของหน้า portal — เหลืองพาสเทลของร้านเบเกอรี่จะหายไปกับพื้น

**แก้:** วัดสีแบรนด์เทียบกับ **พื้นหลังของหน้า** ไม่ใช่เทียบกับตัวอักษรบนปุ่ม
แยกเป็นสองระดับ (< 3.0 ใช้เป็นสีพื้นปุ่มได้อย่างเดียว, < 4.5 ใช้กับหัวข้อใหญ่ได้
แต่ตัวหนังสือเล็กไม่ได้)

### 2.2 `#111111` ทำให้ปุ่มบางสีตกเกณฑ์จริง

พอเขียนเทสต์กวาดสีทั้งช่วงเพื่อ**ยืนยัน**ข้ออ้างในข้อ 2.1 เทสต์กลับล้ม —
เพราะโค้ดใช้ `#111111` (ดำนุ่ม ไม่บาดตา) ไม่ใช่ดำสนิท ซึ่งคอนทราสต์ต่ำกว่า
ดำสนิทเล็กน้อย ทำให้มีสีช่วงแคบๆ ที่ปุ่มตกเกณฑ์จริง

ครั้งแรกแก้ผิด: ถอยไปดำสนิทเฉพาะเมื่อ "ขาวแพ้ soft black" ซึ่งยังพลาด
เทสต์เจอเพิ่มอีกเคส `#0077dd` (ขาว 4.48 / soft 4.21 / ดำสนิท 4.69) —
ขาว *ชนะ* soft แต่ยังตกเกณฑ์อยู่ดี

**แก้:** ดูครบทั้งสามตัวเลือกตามลำดับความน่าใช้ (ขาว → `#111111` → ดำสนิท)
แล้วเลือกตัวแรกที่ผ่านเกณฑ์ เทสต์กวาดสี 4,096 ค่ายืนยันว่าไม่เหลือสีที่ปุ่มอ่านไม่ออก

*บทเรียน:* เทสต์ที่เขียนเพื่อ "ยืนยันสิ่งที่รู้อยู่แล้ว" คือเทสต์ที่จับบั๊กได้จริง

### 2.3 ลิงก์ถูกเผาทิ้งเมื่อฐานข้อมูลสะดุด

`redeem()` ทำตามลำดับ: ตรวจลายเซ็น → ตรวจอายุ → **เผาลิงก์** → อ่านบัญชี

ถ้าการอ่านบัญชีล้มเหลวเพราะ DB สะดุดชั่วขณะ ลิงก์ของลูกค้าถูกใช้ไปแล้ว
ทั้งที่เขายังไม่ได้เข้าระบบ — ต้องขอใหม่โดยไม่รู้ว่าทำอะไรผิด

**แก้:** สลับเป็นอ่านบัญชีก่อนแล้วค่อยเผา การกันใช้ซ้ำยังแน่นเท่าเดิม
เพราะ `consume()` ยังเป็นประตูอะตอมมิกที่มีผู้ชนะรายเดียว ส่วนการอ่านบัญชี
ไม่เปลี่ยนสถานะอะไรจึงทำซ้ำได้ปลอดภัย

### 2.4 ตัวตรวจสองตัวตอบไม่ตรงกัน

`onboardingProgress().readyToInvite` คำนวณจากลำดับขั้น ส่วน `checkReadyToInvite()`
ตรวจเงื่อนไขตรงๆ — พอข้อมูลเพี้ยน (มีโพสต์ในปฏิทินทั้งที่ Brand Brief ยังไม่ครบ)
หน้าจอจะบอก "ส่งลิงก์ได้" แต่พอกดจริงจะถูกปฏิเสธ

**แก้:** ให้ `onboardingProgress` เรียก `checkReadyToInvite` ตัวเดียวกัน
พร้อมเทสต์ที่ไล่ทุกชุดสถานะเพื่อยืนยันว่าสองที่ตอบตรงกันเสมอ

### 2.5 ข้อความ "ขอแก้ไข" ของลูกค้าหายระหว่างทาง

เจอตอนต่อหน้าเว็บ: server action รับ `note` มาจากฟอร์มแล้ว **ไม่ส่งต่อ**
ให้ `decideDemo()` — ลูกค้าพิมพ์ว่าอยากให้แก้อะไรไปสองบรรทัด แล้วทีมงานได้แค่
สถานะ "ขอแก้ไข" เปล่าๆ ต้องโทรกลับไปถาม

ตลกร้ายคือคอมเมนต์ในคอมโพเนนต์เดียวกันเขียนเตือนเรื่องนี้ไว้เองว่า
"ถ้ากดแล้วส่งเลย ทีมงานจะได้แค่ 'ขอแก้' โดยไม่รู้ว่าแก้อะไร"

**แก้:** ส่ง `note` ผ่านตลอดสาย และเก็บไว้ให้ฝั่งทีมงานอ่านย้อนหลังได้

## 3. การแยกข้อมูลระหว่างลูกค้า — จุดที่ผิดแล้วจบธุรกิจ

Client Portal เปิดให้คนนอกองค์กรเข้าถึงระบบเดียวกับที่เก็บข้อมูลลูกค้าทุกราย
ถ้าลูกค้า ก เห็นข้อมูลของลูกค้า ข แม้ครั้งเดียว เอเจนซี่จบทั้งสองรายพร้อมกัน

ระบบแบบนี้รั่วสองทางเสมอ จึงวางด่านไว้สองชั้นสำหรับสองทางนั้น:

**ทางที่ 1 — ลืมใส่เงื่อนไข workspace ใน query**
ทุกฟังก์ชันที่สร้าง view รับ `PortalScope` เป็นอาร์กิวเมนต์แรก
(สร้าง view โดยไม่มีขอบเขตไม่ได้) แล้วกรองด้วย `onlyInScope()`
ปิดท้ายด้วย `assertNoLeak()` ที่เดินทั้ง payload หา `pageId` ที่ไม่อยู่ในขอบเขต
— ตาข่ายชั้นที่สองสำหรับตอนที่คนมาแก้โค้ดในอีกหกเดือนแล้วลืมกรอง

**ทางที่ 2 — เอา id จาก URL ไปใช้ตรงๆ (IDOR)**
`ApprovalService.decide()` ของ M-B **ไม่รู้จักขอบเขตลูกค้า** เพราะออกแบบมาให้
ทีมงานและลิงก์จาก LINE เรียก ซึ่งผูกกับโพสต์ใบเดียวอยู่แล้ว
ถ้า portal ส่ง `postId` เข้าไปตรงๆ ลูกค้าจะกดอนุมัติโพสต์ของคนอื่นได้ด้วยการ
เปลี่ยนตัวเลขใน URL — `decideFromPortal()` จึงเป็นชั้นที่ตรวจความเป็นเจ้าของก่อน

**ข้อความปฏิเสธเหมือนกันทุกกรณี** ทั้ง "ไม่มีของสิ่งนี้" และ "ของสิ่งนี้ไม่ใช่ของคุณ"
— ตอบต่างกันเมื่อไหร่ การไล่เดา id จะบอกได้ว่าอะไรมีอยู่จริงในระบบ
(มีเทสต์เทียบข้อความสองกรณีว่าตรงกันเป๊ะ)

**ฟิลด์ที่ห้ามหลุด** แยกเป็นสองรายการโดยเจตนา: เทียบแบบ "มีคำนี้ในชื่อ"
สำหรับคำเฉพาะ (`cost`, `botConfig`, `token`) และเทียบแบบตรงตัวสำหรับคำทั่วไป
(`flow`, `tone`, `prompt`) — ถ้าเทียบหลวมหมด `cashflow` กับ `milestone`
จะโดนจับผิด แล้วคนจะปิดการตรวจแทนที่จะแก้ข้อมูล

## 4. ความปลอดภัยของ magic link

| เรื่อง | ทำอย่างไร | ทำไม |
|---|---|---|
| อายุลิงก์ | 15 นาที | อีเมลถูกส่งต่อและค้างในกล่องขาเข้าเป็นปี |
| ใช้ซ้ำ | `consume(jti)` แบบอะตอมมิก | ลิงก์ค้างใน history ของเบราว์เซอร์ |
| ไล่เดาว่าใครเป็นลูกค้า | ตอบข้อความเดียวกันทุกกรณี | ไม่งั้นกลายเป็นเครื่องมือให้คู่แข่ง |
| ยิงสแปมใส่อีเมลลูกค้า | จำกัด 5 ครั้ง/15 นาที **รวมอีเมลที่ไม่มีในระบบ** | ถ้านับเฉพาะที่มีจริง จะยิงใส่คนนอกได้ไม่จำกัด |
| เอา session token มาใช้เป็น magic link | ใส่ชนิด (`ml1`/`ps1`) ในส่วนที่เซ็น | ทั้งคู่เซ็นด้วยกุญแจเดียวกัน ลายเซ็นผ่านทั้งคู่ |
| ถอดเพจออกจากสัญญา | ไม่เก็บรายการเพจใน token อ่านใหม่ทุกครั้ง | ถ้าเก็บ เพจที่ถอดแล้วยังเปิดดูได้อีก 7 วัน |
| จบสัญญาแล้วต้องตัดทันที | `sessionEpochOf()` — ขยับค่าแล้วทุก session ตายพร้อมกัน | session 7 วันที่ยกเลิกไม่ได้คือปัญหาจริงตอนเลิกจ้าง |
| ลิงก์อยู่ใน log | ไม่ log URL เลย ตัว `PortalAuth` ไม่รับ logger | ลิงก์คือรหัสผ่านชั่วคราว (กฎข้อ 3 โดยอนุโลม) |

**ที่รู้ตัวว่ายังไม่ได้ทำ:** ไม่ได้จำกัดจำนวนครั้งของ `redeem()` — token เซ็นด้วย
HMAC-SHA256 การเดาจึงไม่คุ้ม แต่ถ้าเปิดใช้จริงควรมี rate limit ระดับ IP
ที่ชั้น reverse proxy อยู่แล้ว

## 5. เรื่องที่ตัดสินใจไว้ พร้อมเหตุผล

### 5.1 โลโก้: ไม่รับ SVG

SVG เป็นเอกสาร XML ที่ฝัง `<script>` และ `<foreignObject>` ได้ พอเอามาแสดง
ในหน้าเราก็กลายเป็นโค้ดที่รันในโดเมนเรา — ลูกค้าที่มีโลโก้เป็น SVG
ให้แปลงเป็น PNG ตอนอัปโหลด ตรวจเพิ่มด้วยว่าเป็น `https` และไม่มีรหัสผ่านฝังใน URL

### 5.2 subdomain: กันชื่อที่ใช้หลอกได้

นอกจากชื่อของระบบเอง (`api`, `www`) ยังกันชื่อที่ทำให้เข้าใจผิดว่าเป็นหน้าทางการ
(`secure`, `login`, `billing`) ซึ่งเป็นวัตถุดิบชั้นดีของอีเมลหลอกลวง
และห้ามขึ้นต้นด้วย `xn--` เพราะเป็นรูปแบบ punycode ที่ใช้จดชื่อหน้าตาเหมือนแบรนด์อื่น

### 5.3 เลขบัตรประชาชน: ตรวจ checksum จริง ไม่ใช่แค่นับหลัก

สเปกข้อ M6 ห้ามเก็บเลขบัตรประชาชน บอทไม่ถามอยู่แล้วแต่ลูกค้าพิมพ์เองมาได้
`scrubProhibitedPii()` จึงปิดไว้ตอนแสดงผลและตอน export

**ตรวจ checksum ตามสูตรจริง ไม่ใช่เบลอทุกอย่างที่ยาว 13 หลัก** — เลขออเดอร์
13 หลักมีอยู่จริงและเยอะ ถ้าเบลอเกินไป ลูกค้าจะอ่านข้อมูลของตัวเองไม่ได้
ซึ่งทำให้ฟีเจอร์ใช้ไม่ได้ทั้งฟีเจอร์

### 5.4 Export CSV: กันสูตรที่รันตอนเปิดไฟล์

ชื่อที่ขึ้นต้นด้วย `=` `+` `-` `@` ถูก Excel ตีความเป็นสูตรและรันทันทีที่เปิดไฟล์
(CSV injection) — เติมอัญประกาศเดี่ยวนำหน้าก่อนเขียนลงไฟล์

### 5.5 รายงาน: ตัดเมตริกดิบ 40 ตัวทิ้ง

`MonthlyReport` มี `allMetrics` ครบทุกตัว แต่ portal ส่งเฉพาะ `highlights`
รายงานที่มีตัวเลขสี่สิบตัวไม่ได้แปลว่าทำงานเยอะ แต่แปลว่าไม่มีใครอ่าน

### 5.6 Onboarding: ลำดับขั้นคือเนื้อหาหลัก ไม่ใช่รายการติ๊กถูก

สิ่งที่ทำให้ onboarding ยืดไม่ใช่แต่ละขั้นช้า แต่คือการทำผิดลำดับแล้วต้องย้อนกลับ
— สร้างปฏิทินก่อนกรอก Brand Brief จะได้โพสต์กลางๆ ที่ต้องทิ้งทั้งเดือน
`requires` ของแต่ละขั้นจึงเป็นหัวใจ และ "ขั้นถัดไป" ชี้ไปที่ขั้นที่ **ทำได้แล้ว**
ไม่ใช่ขั้นแรกที่ยังไม่เสร็จ (ไม่งั้นคนไปนั่งงงหน้าจอที่กดอะไรไม่ได้)

รวมเวลาทั้งหมด 30 นาทีพอดีตามเกณฑ์รับงาน มีเทสต์ล็อกไว้ว่าห้ามเกิน
